## 1. 结论摘要

### 1.1 一句话结论

当前平台的 RAG 是"**外挂 Dify 单引擎**"，检索主链路已经打通。双引擎方案可以复用现有业务入口，但不能直接在现有 `KnowledgeBaseProvider` 上增加一个实现：该接口仍依赖 Dify DTO、`externalDatasetId` 和外部数据集生命周期。实施前必须先把它重构为引擎无关契约，再接入 Dify 与 Spring AI 两个适配器。自研引擎采用版本化索引、异步索引任务和可灰度切换，并补齐检索证据、质量门禁与成本归集能力。

### 1.2 主张

1. **共存不是二选一，而是三级并列**：系统级默认引擎、知识库级引擎、Agent 调试时的临时覆盖，三者优先级明确、可解释、可审计。
2. **切换粒度是"索引版本"，不是"知识库"**。知识库是逻辑资产，永不迁移；引擎、模型、切分参数共同构成一个不可变的**索引版本（Index Version）**。切换 = 指针切换，回滚 = 指针回切，两个索引可长期双跑。
3. **索引版本与异步任务是一期基础设施**。原始文件、解析、嵌入和发布都必须围绕版本与源文件快照实现，不能先做单版本自研再在后期补版本管理。
4. **相同维度不等于相同向量空间**。文本模型与多模态模型生成的向量不能因为都是 1024 维就混入同一 HNSW 索引。文本空间与多模态空间必须分别召回，再通过 RRF 或经评测校准的融合算法合并排名。
5. **质量必须可测量**。本文定义检索指标、生成指标和冻结评测集，未达标不允许切流。
6. **成本按知识库与索引版本归集**。嵌入、检索、重排、OCR、对象存储和生成上下文必须分别记账。
7. **默认不启用重排（Rerank）**。混合检索可先使用 RRF 或权重融合；仅在评测显示"召回正确但排序靠后"时开启重排。
8. **多格式解析是最大交付风险**。Dify 的主要成熟度来自文档处理管线，自研一期应先支持高频文本格式，再按真实扫描件占比接入 OCR。
9. **配置必须可选择、可验证、可回滚**。平台需要模型中心，知识库需要索引版本向导和召回测试。Embedding、多模态、Caption 与 Rerank 模型不能继续硬编码在页面里。

### 1.3 建议的分期

| 阶段 | 目标 | 关键交付 | 成功判据 |
|------|------|---------|---------|
| P0 | 安全与契约冻结 | 轮换已暴露凭据、修正 Dify 检索参数、重构 Provider 契约、PgVector/模型连通性验证、冻结基线评测集 | 安全问题清零，接口与数据模型可供多人并行开发 |
| P1 | 文本自研引擎可用 | 原始文件存储、索引版本、异步任务、常用格式解析、文本 Embedding、向量检索、证据对象、召回测试 | 单库可完整索引、检索、定位证据、重试和回滚 |
| P2 | 质量与切流 | 中文关键词召回、RRF、父子分块、按需重排、质量门禁、影子流量 | 同集评测不劣于 Dify，发布与回滚可演练 |
| P3 | 解析与治理增强 | OCR、更多格式、成本看板、SLA、模型中心、知识库设置完善 | 可观测、可计价、可自助配置 |
| P4 | 多模态与差异化 | 文本与多模态双空间检索、语义缓存、GraphRAG 试点、私有化全离线 | 图文检索通过独立评测，新增能力有明确业务收益 |

## 3. 目标与非目标

### 3.1 目标（一期必须达成）

1. **双引擎共存**：同一平台内 Dify 外挂与 Spring AI 自研并存，互不阻塞。
2. **灵活切换**：支持系统默认、知识库级、调试临时三级选择；切换行为对调用方（Agent、开放 API）透明。
3. **平滑迁移**：已有 Dify 知识库可原地继续使用，也可在不停机前提下渐进迁移到自研，迁移期间双跑。
4. **质量不弱于 Dify**：以冻结评测集为准，检索指标与生成指标分别达到或超过外挂基线。
5. **成本可计量**：按知识库归集五类成本，可出月报。
6. **权限一致**：自研引擎必须继承现有的所有权、共享授权（VIEW/USE）、审计与开放平台契约，不得出现新的越权面。

### 3.2 非目标（明确不做，避免范围蔓延）

1. 一期不追求替换 Dify 在**工作流编排（Workflow/Chatflow）**上的能力——那不属于知识库范畴。
2. 一期不做多模态生成（图像/视频理解生成），仅做多模态**入库与检索**（图片、扫描件、表格）。**图文跨模态检索的详细设计见第 18 章**。
3. 一期不引入独立向量数据库（Milvus/Qdrant 等），优先复用现有 PostgreSQL + pgvector，理由见第 7 章成本论证。
4. 一期不做跨租户物理集群隔离，沿用单实例 + 逻辑隔离。
5. 不承诺"任意格式零损耗解析"，而是明确支持矩阵与降级策略（见第 8 章）。

### 3.3 设计原则

1. **逻辑与物理分离**：知识库是逻辑资产，索引是物理产物，二者解耦。
2. **接口先于实现**：所有引擎差异收敛在 Provider 接口内，上层不感知。
3. **失败可解释**：不静默回退、不静默降级，任何回退必须留痕并可见。
4. **默认拒绝**：未知引擎、未知权限、缺失版本一律拒绝，而非猜测。
5. **质量门禁先于切流**：未通过评测的引擎不得承接生产流量。

## 4. 总体架构

### 4.1 分层视图

```
┌──────────────────────────────────────────────────────────────┐
│  交互层  Dashboard 知识库面板 / Debug 编排 / 引擎对比页 / 开放 API │
├──────────────────────────────────────────────────────────────┤
│  编排层  KnowledgeOrchestrator（引擎选择 + 检索编排 + 证据组装）    │
│          - 三级引擎决议（系统 / 库 / 调试覆盖）                    │
│          - 检索后处理：重排 → 去重 → 压缩 → token 预算裁剪          │
│          - 证据对象组装（含引用、页码、分数、耗时、成本）            │
├──────────────────────────────────────────────────────────────┤
│  引擎层  KnowledgeBaseProvider（策略接口，已存在）                 │
│          ├── DifyKnowledgeBaseProvider      （外挂，已实现）      │
│          └── SpringAiKnowledgeBaseProvider  （自研，本次新增）     │
├──────────────────────────────────────────────────────────────┤
│  能力层  切分器 / 解析器(OCR) / 嵌入 / 重排 / 改写 / 缓存           │
│          全部按"能力槽位"注册，引擎按槽位取用，可混搭                │
├──────────────────────────────────────────────────────────────┤
│  存储层  PostgreSQL（业务表 + pgvector 向量表 + 全文检索）          │
│          对象存储（原始文件，本地/MinIO/OSS 可切）                  │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 关键抽象

**第一个抽象是"索引版本（Index Version）"**。这是整个设计的支点。

一个索引版本 = 引擎 + 解析配置 + 切分配置 + 嵌入模型 + 维度 + 距离度量 + 重排模型 + 状态。它是**不可变**的：任何一项变化都产生新版本，而非原地修改。理由很实际——嵌入模型或维度一旦改变，已有向量全部作废，原地修改必然导致新旧向量混用、召回结果不可信。

```
knowledge_bases (逻辑资产，永远只有一个)
    ├── active_index_version_id (当前主流量指针)
    └── knowledge_index_versions (1..N，物理索引，各自独立)
            ├── version_no, engine_type, status
            ├── parse_config, chunk_config, embedding_model, dimension, distance
            ├── rerank_model, search_method, top_k, score_threshold
            └── source_snapshot_no, config_hash, provider_handle
    └── knowledge_documents (文档，跨版本共享的原始资产)
            └── document_index_states (每文档 × 每版本的索引状态)
```

**第二个抽象是"引擎无关契约"**。现有 `KnowledgeBaseProvider` 的方法签名依赖 `DifyDatasetDto`、`externalDatasetId` 和 Dify 数据集生命周期，不能作为自研实现的稳定边界。P0 必须先拆成以下契约：

| 契约 | 输入 | 输出 | 说明 |
|------|------|------|------|
| `RagEngineProvider` | `IndexBuildSpec` | `EngineIndexHandle` | 创建或绑定一个物理索引，不泄露 Dify DTO |
| `DocumentIngestionService` | `SourceRevision` + `IndexVersion` | `IndexJobId` | 异步索引入口，负责幂等、重试和进度 |
| `RetrievalService` | `RetrievalRequest` | `RetrievalResult` | 统一返回证据、分数构成、耗时、成本和引擎决议 |
| `EngineCapabilityService` | 引擎与通道 | `EngineCapabilities` | 告诉 UI 支持的格式、模型、维度和多模态能力 |

Dify 适配器把上述契约翻译为 Dataset API；Spring AI 适配器把契约翻译为本地对象存储、解析任务与 PgVector 查询。上层服务只保存 `provider_handle`，不保存特定厂商 DTO。

**第三个抽象是"能力槽位"**。检索质量由五个槽位决定，每个槽位是可替换实现，与引擎解耦：

| 槽位 | 职责 | 外挂实现 | 自研实现 |
|------|------|---------|---------|
| Parser | 文件 → 结构化文本 | Dify 内部管线 | Tika + OCR 管线 |
| Chunker | 结构化文本 → 切片 | Dify 内部管线 | 递归/父子/语义切分器 |
| Embedder | 切片 → 向量 | Dify 内部调用 | Spring AI EmbeddingModel |
| Retriever | 查询 → 候选集 | Dify /retrieve | 向量 + 全文双路召回 |
| Reranker | 候选集 → 精排 | Dify 内置 rerank | qwen3-rerank / 本地重排 |

能力槽位用于定位质量和替换实现，但一期不承诺跨引擎混搭。"Dify 解析 + 自研检索"需要稳定的解析产物导出契约，只有完成源文件与解析产物校验后才能开放，避免把概念能力误写成一期交付。

**第四个抽象是"向量空间"**。向量能否比较由模型与空间标识共同决定，而不是只由维度决定。每条向量必须记录 `space_type`、`model_id`、`model_revision`、`dimension` 和 `distance_type`。文本切片与图片 Caption 可以进入同一个文本空间；图片视觉向量和用于以文搜图的查询文本必须由同一个多模态模型编码，并进入独立的多模态空间。两个空间分别召回后做排名融合。

## 5. 双引擎共存模型

### 5.1 三级引擎决议

```
生效引擎 = 调试临时覆盖  >  知识库绑定引擎  >  系统默认引擎
```

| 层级 | 作用域 | 谁可设置 | 持久化 | 典型用途 |
|------|--------|---------|--------|---------|
| L1 系统默认 | 全平台新库 | 超级管理员 | `platform_settings` | 平台统一技术路线 |
| L2 知识库绑定 | 单个知识库 | 库所有者 / 管理员 | `knowledge_index_versions.engine_type` | 按数据敏感度选引擎 |
| L3 调试覆盖 | 单次调试请求 | 有调试权限者 | 请求态，不落库 | 灰度对比、问题定位 |

调试覆盖必须由前端显式提交到后端，并由后端校验权限、配额和目标版本。前端会话态只负责记住用户选择，不能作为实际路由依据。

**决议必须可解释**。检索响应里强制回传 `engineResolution` 对象：

```json
{
  "engineResolution": {
    "effectiveEngine": "SPRING_AI",
    "source": "KB_BINDING",
    "chain": [
      { "level": "L1", "value": "DIFY", "overridden": true },
      { "level": "L2", "value": "SPRING_AI", "overridden": false },
      { "level": "L3", "value": null }
    ],
    "indexVersionNo": 3,
    "fallback": false
  }
}
```

### 5.2 为什么以"索引版本"而非"知识库"为切换单位

这是本文最重要的设计决策，值得单独论证：

1. **不可逆性**：向量与嵌入模型强绑定。若允许在知识库上直接改引擎，等于要求"就地重建全部向量"，重建期间该库不可用，且失败后无法回退到旧的可用状态。
2. **可比性**：质量对比必须在**同一批文档、同一批查询**上进行。版本化天然满足——两个版本挂在同一个逻辑库上，共享同一份原始文档与同一份评测查询，指标可直接对齐。
3. **渐进迁移**：可以对同一库建新版本，在后台慢慢索引（可能几小时到几天），索引完成并评测通过后再执行"发布"，指针切换是瞬时的。
4. **回滚成本**：回滚主要是切换指针，不涉及数据搬运，操作耗时很低。但旧索引、对象存储和对应模型通道必须继续保留，因此不能称为零成本。

### 5.3 版本状态机

```
DRAFT ──开始构建──> BUILDING ──构建完成──> VALIDATING ──评测通过──> READY
  │                     │                       │                      │
  │                     └──失败──> FAILED       └──未通过──> REJECTED │
  └──删除                                                         │ 发布
                                                                   ▼
                                             knowledge_bases.active_index_version_id
                                                                   │
                                                        旧版本保留为 RETIRED
```

| 状态 | 可检索 | 可编辑配置 | 可删除 | 说明 |
|------|--------|-----------|--------|------|
| DRAFT | 否 | 是 | 是 | 配置中 |
| BUILDING | 否 | 否 | 否 | 索引中，可取消 |
| VALIDATING | 否 | 否 | 否 | 跑评测集 |
| READY | **是，仅调试/影子流量** | 否 | 否 | 已就绪待发布 |
| RETIRED | **是，仅回滚/对比** | 否 | 是* | 曾接主流量，仍保留完整索引 |
| FAILED / REJECTED | 否 | 否 | 是 | 可按相同配置重试；调整配置必须创建新版本 |

主流量是否生效只由 `knowledge_bases.active_index_version_id` 决定，不再同时维护 `status=ACTIVE` 与 `is_active` 两套真相。发布操作在事务中锁定知识库行，校验目标版本为 READY 后原子更新指针。旧版本改为 RETIRED；若仍在回滚窗口、影子任务或评测报告中被引用，不允许删除。

### 5.4 多版本并存与资源上限

同库可同时存在：1 个主流量指针、N 个 RETIRED、1 个 BUILDING、多个受控 READY。为避免滥用，设硬约束：
- 单库版本数上限 5（可配置）；
- BUILDING 状态单库仅 1 个（避免并发索引争抢嵌入配额）；
- READY 状态超过 7 天未发布则提示；超过 30 天仅在没有影子、评测或发布计划引用时自动回收。

## 6. 切换机制与平滑迁移

### 6.1 三种切换场景

| 场景 | 操作路径 | 停机 | 可回滚 | 目标耗时 |
|------|---------|------|--------|---------|
| A. 新建库直接用自研 | 创建时选引擎 | 无 | 是（重建） | 即时 |
| B. 存量库迁自研 | 建版本 → 索引 → 评测 → 发布 | 无 | 是（指针回切） | 索引耗时 + 评测 |
| C. 临时对比验证 | 调试页切换覆盖引擎 | 无 | 不涉及 | 即时 |

### 6.2 场景 B 的详细流程

```
Step 1  管理员在库详情页点击「新建索引版本」
        → 复制当前主流量版本配置为草稿，默认引擎切为 SPRING_AI
        → 前端预检：显示预计 token 量、预计费用、预计耗时

Step 2  确认后进入 BUILDING
        → 逐文档：取原始文件（本地留存或从 Dify 回拉）
        → 解析（含 OCR）→ 切分 → 嵌入 → 写向量表
        → 进度可实时查看，支持暂停/继续/取消

Step 3  BUILDING 完成 → 自动进入 VALIDATING
        → 使用该库绑定的评测集（若无则用平台通用集）自动跑分
        → 输出对比报告：新版本 vs 当前主流量版本的逐项指标差异

Step 4  人工决策
        → 通过：点击「发布」，指针切换，旧版本转 RETIRED
        → 不通过：点击「驳回」，版本转 REJECTED，可调整配置后重建
        → 也可「双跑观察」：旧版本继续接主流量，新版本以影子模式接少量流量

Step 5  回滚预案
        → 上线后 7 天内发现异常，一键切回 RETIRED 版本
        → 回滚耗时 = 一次指针更新
```

### 6.3 影子流量（Shadow Mode）

双跑观察是风险最高的阶段，也是最能体现工程成熟度的能力：

- **主链路**：请求走 `knowledge_bases.active_index_version_id` 指向的版本，结果正常返回用户。
- **影子链路**：同一请求异步并行发往 READY 版本，结果只记录、不返回。
- **记录内容**：两个版本的召回集合交集/差集、分数分布、重排顺序差异、耗时差异、token 成本差异。
- **启用条件**：仅管理员可开，仅对指定库生效，影子调用成本单列，不影响用户体感延迟（异步 + 超时熔断）。

这样，上线决策依据不是"感觉新引擎更好"，而是"在 500 次真实请求上，新引擎独有召回率 X%、重叠率 Y%、平均耗时 +Z ms、成本 +W 元"。

### 6.4 迁移的一致性保障

| 风险 | 保障措施 |
|------|---------|
| 迁移期间文档增删导致两版不一致 | 构建开始时冻结 `source_snapshot_no`；后续变更生成新的 `source_revision`，构建完成后按序补齐或明确标记版本落后 |
| 迁移中途失败留下脏数据 | 写入以 `index_version_id + source_revision_id + chunk_hash` 幂等；失败版本进入 FAILED，后台清理任务回收数据 |
| 原始文件丢失导致无法重建 | 强制本地留存原始文件（见 6.5），存量库执行一次性回拉 |
| 评测集缺失导致质量不可判 | 未绑定评测集的库不允许发布新版本（可申请豁免，需管理员二次确认并留痕） |

### 6.5 原始文件资产治理（针对 F8 缺陷）

**这是必须优先解决的资产风险**：当前上传的文档本体只存在 Dify，本地只有元数据。若 Dify 实例故障或迁移，历史文档将无法重建索引。

目标状态：**原始文件双留**。

```
对象存储抽象 ObjectStorageService
  ├── LocalFileStorage      （默认，./data/kb-files/{kbId}/{docId}/{filename}）
  ├── MinIOStorage          （推荐生产）
  └── OssStorage            （阿里云/腾讯云 OSS）
```

要点：
1. 上传时先进行 MIME 嗅探、扩展名校验、压缩包炸弹检查和恶意文件扫描，再写入对象存储。对象保存成功并写入 `source_revision` 后，通过 Outbox 异步分发给 Dify 或自研索引任务；不得在一次 HTTP 请求中用长事务串联对象存储、Dify 和数据库。
2. 存量文档执行一次性回拉任务：从 Dify 拉取文档内容，回写本地存储；对无法回拉的（Dify 未保留原文）标记 `source_missing`，并在 UI 明示"该文档不可重建索引"。
3. 原始文件走**受控下载接口**，不再使用 `/uploads/**` 静态暴露（针对 F12 缺陷）。

## 7. 自研引擎技术方案

### 7.1 向量存储选型论证

| 方案 | 引入成本 | 运维成本 | 能力上限 | 适用判断 |
|------|---------|---------|---------|---------|
| **PostgreSQL + pgvector** | 极低（已有 PG） | 极低（复用备份/监控） | 百万级向量足够 | ✅ **推荐一期** |
| 独立 Qdrant / Milvus | 高（新组件） | 高（新集群） | 亿级、高级过滤 | 二期按需 |
| Elasticsearch + 向量 | 高 | 高 | 混合检索强 | 除非已有 ES |
| 纯内存（无持久化） | 极低 | 无 | 不可用于生产 | ❌ 排除 |

**选 PgVector 的四条理由**：

1. **架构收敛**：平台已经重度依赖 PostgreSQL（JPA + Flyway），向量与文档元数据可以在单次批量落库时使用本地事务。但解析、OCR 和 Embedding 包含外部调用，完整索引链路仍是异步最终一致，必须依赖任务状态、Outbox、幂等写入与补偿，不能用长数据库事务包住整个流程。
2. **元数据过滤免费**：权限过滤条件（owner、共享、状态）直接是 SQL 的 WHERE 条件，与向量检索在同一条 SQL 里完成。独立向量库需要把权限过滤下推成其专有 DSL，且难以与业务表关联。
3. **成本为零增项**：不新增实例、不新增运维面板、不新增备份链路。
4. **规模够用**：PgVector 适合作为一期候选，但百万级表现取决于维度、过滤条件、内存、HNSW 参数和数据分布，必须用本平台数据压测。不要默认按知识库建表，以免产生大量表和索引；优先采用共享表加受控分区，并验证多租户过滤后的召回数量与延迟。

**选择时需注意的关键约束（已核实）**：

- 需要 PostgreSQL 安装 `vector`、`hstore`、`uuid-ossp` 三个扩展（`vector` 需单独安装）。
- **HNSW 索引对维度有限制：pgvector 官方文档指出 HNSW 索引最多支持 2000 维**。当前 Dify 侧默认使用的是 `text-embedding-v3`（1024 维），若自研选用 v4 的 2048 维则**刚好在临界点上**，而通义 `qwen3.7-text-embedding` 的 2560 维**超出 HNSW 上限**。因此自研的嵌入维度策略必须显式约束为 **≤1024 维**（推荐 1024），这是硬性技术边界，不是偏好。
- Spring AI 已提供官方 starter：`spring-ai-starter-vector-store-pgvector`，配置项含 `index-type`（HNSW/IVFFlat/NONE）、`distance-type`（默认 COSINE_DISTANCE）、`dimensions`、`initialize-schema`。注意：**较新版本中 schema 自动初始化默认关闭，需显式开启**。
- 本平台使用 Flyway 管理表结构，因此建议**关闭 Spring AI 的 schema 自动初始化**，改由 Flyway 迁移脚本创建向量表，避免两套建表机制冲突（这是很容易踩的坑）。

**物理表约束**：Spring AI PgVector 的维度绑定在向量列创建时。平台必须在 P0 二选一并写入 ADR：

1. 一期把所有文本索引统一固定为 1024 维，每个多模态空间使用独立物理表；或
2. 按 `space_type + model_revision + dimension` 路由到有限数量的物理表与 HNSW 索引。

禁止在同一个 HNSW 索引中混放不同模型或不同维度的向量。模型升级即使维度不变，也必须产生新的向量空间和索引版本。

### 7.1.1 异步索引任务与一致性

索引链路采用可恢复的状态机：

```
文件写入对象存储
  → 写 source_revision 与 outbox_event
  → 领取 index_job 租约
  → 解析并保存 parse_artifact
  → 生成稳定 chunk_hash
  → 分批 Embedding
  → 幂等写入向量与元数据
  → 校验文档数、块数、向量数和配置哈希
  → VALIDATING / READY
```

`knowledge_index_jobs` 至少包含 `status`、`attempt`、`lease_owner`、`lease_until`、`checkpoint`、`last_error_code`、`next_retry_at` 和取消标记。Worker 通过租约或 `FOR UPDATE SKIP LOCKED` 领取任务；进程退出后租约到期可被其他实例接管。每个阶段都必须可重入，取消操作停止后续步骤并由异步清理任务回收该版本的数据。

### 7.1.2 最小数据模型与约束

P0 必须把以下结构落实为 Flyway 迁移草案，工程师不得继续依赖 `ddl-auto=update` 推导生产表结构。

| 表 | 关键字段 | 必须约束 |
|----|---------|---------|
| `knowledge_bases` | `active_index_version_id`, `source_snapshot_no` | 发布时锁行并原子切换指针 |
| `knowledge_source_revisions` | `document_id`, `revision_no`, `object_key`, `sha256`, `mime_type`, `size` | `(document_id, revision_no)` 唯一；对象不可原地覆盖 |
| `knowledge_index_versions` | `engine_type`, `provider_handle`, `config_json`, `config_hash`, `source_snapshot_no`, `status` | `(knowledge_base_id, version_no)` 与 `config_hash` 受控唯一；BUILDING 后配置不可变 |
| `knowledge_index_jobs` | 租约、重试、checkpoint、错误码、进度 | 同一版本同一阶段只允许一个有效任务 |
| `knowledge_document_index_states` | 文档修订、版本、块数、向量数、状态 | `(index_version_id, source_revision_id)` 唯一 |
| `knowledge_chunks` | `chunk_hash`, `parent_chunk_id`, 页码、偏移、内容、元数据 | `(index_version_id, chunk_hash)` 唯一；保留来源定位 |
| `knowledge_chunk_embeddings_*` | `chunk_id`, `space_type`, `model_revision`, `embedding` | 每个物理表只有一个维度与距离类型；向量与空间配置一致 |
| `rag_retrieval_traces` | 请求、版本、阶段耗时、候选数、成本、错误码 | 查询内容按脱敏和保留策略存储 |
| `rag_evaluation_*` | 数据集版本、用例、运行、逐项结果 | 已用于发布门禁的数据集版本不可修改 |

所有子表包含 `knowledge_base_id` 或可通过受约束外键唯一回溯到知识库。删除知识库采用“先禁止访问、再异步物理清理”的流程，并记录对象、块、向量和评测数据的保留策略。

### 7.2 检索管线设计（自研）

自研检索不是单次向量查询，而是可编排的六段管线。每一段都可独立开关与调参，并记录分段耗时。

```
用户 Query
   │
   ├─[1] 查询理解    按需改写 / 多查询扩展 / 指代消解（低温度模型）
   │
   ├─[2] 双路召回    向量召回(topK_v) + 全文召回(topK_k, PG tsvector 或 pg_trgm)
   │
   ├─[3] 融合        RRF（倒数排名融合）或加权分数融合
   │
   ├─[4] 重排        qwen3-rerank / 本地 CrossEncoder，取 topN
   │
   ├─[5] 后处理      去重（同文档相邻块合并）+ 父子块展开（取父块上下文）+ 压缩
   │
   └─[6] 预算裁剪    按 token 预算裁剪，保证注入不超上下文窗口
```

**各段设计要点**：

| 段 | 自研做法 | 相对 Dify 的增量价值 |
|----|---------|-------------------|
| 查询理解 | `RewriteQueryTransformer` / `MultiQueryExpander`；仅对多轮指代、短且歧义明显的查询启用，保留原查询并记录改写结果 | 避免默认改写造成实体漂移，同时支持多轮检索 |
| 双路召回 | 向量 + PostgreSQL 全文双路并发 | 中文全文检索需额外配置分词（见下） |
| 融合 | RRF 默认，可选加权 | RRF 对分数尺度不敏感，比纯加权更稳 |
| 重排 | 外接 qwen3-rerank（已核实：0.5 元/百万 token，最大输入 30000，文本单模态） | 与 Dify 同款模型，可控性更强 |
| 后处理 | 父子块展开、相邻块合并、压缩 | Dify 的父子分块在 1.9+ 有，但配置自由度受限 |
| 预算裁剪 | token 预算制，替换现有"12 块 × 1500 字符"硬编码（F4 缺陷） | 消除长文档被截断问题 |

**中文全文检索的现实约束**：PostgreSQL 内置分词**不识别中文**（`to_tsvector('simple', ...)` 会把整句当一个 token）。三个可选路径：

1. **`pg_trgm` 三元组匹配**：零额外组件，中文效果可接受，适合一期快速落地。**推荐一期**。
2. **`zhparser` / `pg_jieba` 扩展**：中文分词效果好，但需编译安装扩展，增加部署复杂度。
3. **`pg_bigm`**：二元组，中文支持好，同样需安装扩展。

**建议**：一期用 `pg_trgm` 确保能落地，同时把分词实现抽象为 `KeywordRetriever` 接口，二期按效果替换。

### 7.3 切分策略

| 策略 | 适用 | 实现要点 |
|------|------|---------|
| 递归字符切分 | 通用文本（默认） | 分隔符优先级：`\n\n` → `\n` → `。！？` → `. ` → 空格；重叠 10%~15% |
| 父子分块 | 需要完整上下文的长文（手册、合同、政策） | 子块 200~400 字符用于召回，父块 1000~2000 字符用于生成；检索命中子块后回取父块 |
| 语义切分 | 主题跳跃明显的长文 | 相邻句向量相似度低于阈值处切分；成本高，仅对高价值文档启用 |
| 结构化切分 | FAQ、表格、Excel | 按行/问答对为原子单位，每行独立成块并携带表头 |
| 代码切分 | 代码文件 | 按函数/类边界切分 |

**推荐默认参数**（可实测调整）：块大小 512 token、重叠 64 token、父子模式开启、父块上限 2048 token。

**分隔符必须支持自定义与预览**。Dify 1.9 的父子分块允许分别配置父/子分隔符与最大长度（已核实的资料显示支持 `paragraph` 与 `full_doc` 两种父块模式）。自研侧要对齐这些可调项，并且提供**切分结果实时预览**（这是现有 UI 完全缺失的能力，见第 12 章）。

### 7.4 检索参数体系（修正 F7 缺陷）

自研版本必须让这些参数**真正生效并可观测**，同时**回头修正 Dify Provider 的检索参数下发**（当前 retrieve 只发 query）：

| 参数 | 说明 | 默认 |
|------|------|------|
| `topKVector` | 向量召回条数 | 20 |
| `topKKeyword` | 全文召回条数 | 20 |
| `topNAfterRerank` | 重排后保留 | 5 |
| `scoreThreshold` | 相似度阈值，按向量空间与评测集校准，低于丢弃 | 默认关闭 |
| `fusionMode` | RRF / WEIGHTED | RRF |
| `vectorWeight` / `keywordWeight` | 加权融合权重 | 0.7 / 0.3 |
| `maxContextTokens` | 注入上下文 token 上限 | 3000 |
| `rerankEnabled` | 是否重排 | **false（默认关闭，按需开启）** |
| `rewriteMode` | OFF / AUTO / ALWAYS | AUTO（仅多轮歧义查询） |
| `expandParent` | 是否展开父块 | true |

**关于"重排默认关闭"的说明（重要设计决策）**：

Dify 的官方行为是——向量检索、全文检索、混合检索三种模式下的 **Rerank 模型均默认关闭**，混合检索模式下用户可直接使用"权重设置"进行融合而**无需配置 Rerank 模型 API**（已核实 Dify 官方文档）。自研侧对齐这一默认，理由同样成立：

1. **混合检索本身已是完整方案**。向量召回负责语义泛化，全文召回负责专有名词与精确匹配，权重/RRF 融合后直接可用。**重排是质量增强项，不是必需项**。
2. **默认不重排 = 默认零重排成本**。第 10 章测算显示重排是持续性成本主项（大规模月成本万元级），默认关闭意味着新库在未明确需要时**不产生这笔费用**。
3. **按需开启，且开启门槛明确**。当评测显示"召回对了但排序不佳"时再开启重排——这是有依据的决策，而非默认堆料。

**⚠️ 一个必须注意的差异点**：Dify 文档明确指出「**TopK 和 Score 设置仅在 Rerank 阶段生效**，要应用这些设置中的任何一项，需要添加并启用 Rerank 模型」。即 Dify 下不开重排时，TopK 与 Score 阈值**不生效**。

**自研侧不沿用这个限制**：TopK（双路召回各自条数）与 `scoreThreshold` 在召回阶段独立生效，与是否开启重排解耦。但阈值不能全平台固定为 0.25：不同模型、距离度量和融合方式的分数分布不同，必须按向量空间保存校准结果。RRF 分数用于排序，不应在 UI 中伪装成 0~1 的相关概率。

**开启重排的判据**（建议写入运维手册）：评测中观察到 `Recall@10` 达标但 `Hit@5` / `NDCG@10` 偏低——说明**该召回的召回了、但没排到前面**，此时启用重排收益最大。

### 7.5 检索证据对象（修正 F5 缺陷）

```java
public record RetrievedChunk(
    String chunkId,          // 切片唯一标识
    String documentId,       // 所属文档
    String parentChunkId,    // 父块（可空）
```

## 8. 多格式解析与 OCR 方案

> 这一章是"自研不弱于 Dify"的关键战场。Dify 的优势很大程度来自开箱即用的文档处理管线；自研若在这一步偷懒，后面所有检索优化都是白费。

### 8.1 支持矩阵与降级策略

| 类型 | 解析方案 | 是否需 OCR | 一期 | 质量目标 |
|------|---------|-----------|------|---------|
| TXT / MD | 直读，编码探测（UTF-8/GBK） | 否 | ✅ | 无损 |
| PDF（文本层） | PDFBox 提取文本 + 版面坐标 | 否 | ✅ | 保留段落与标题层级 |
| PDF（扫描件） | 渲染为图 → OCR | **是** | ✅ | 中文准确率 ≥ 95% |
| DOCX | POI 提取段落、标题、表格 | 否 | ✅ | 表格转 Markdown |
| XLSX / CSV | POI / 直读，按行成块 + 表头携带 | 否 | ✅ | 表头不丢 |
| PPTX | POI 提取文本框与备注 | 否 | ✅ | 按页成块 |
| 图片 | OCR | **是** | ✅ | 同扫描件 |
| 网页 URL | 正文抽取（Readability 类算法） | 否 | ⏳二期 | 去导航去广告 |
| 复杂表格 | 版面分析 + 表格结构还原 | 视情况 | ⏳二期 | 合并单元格可还原 |
| 公式 | 公式识别 → LaTeX | 是 | ⏳二期 | 简单公式可读 |
| 音视频 | ASR 转写 | 是 | ❌ 不做 | 明确排除 |

**降级原则**：任何文档解析失败都必须给出**明确原因**（加密、损坏、不支持格式、OCR 置信度过低），并落入 `FAILED` 状态，而不是静默产生空文档。这一点现有实现是缺失的（`indexing_status` 只透传 Dify 状态）。

> **OCR 前置判断**：是否需要 OCR 取决于文档是否含文本层，而这**随客户文档而变、设计期无法预设**。判断方法、硬件配置要求与可插拔设计见 8.2.1 ~ 8.2.3。**架构要求不是"要不要做 OCR"，而是"OCR 必须随时可插拔、开启后立刻可用"。**

### 8.2 OCR 选型论证

| 方案 | 精度 | 成本 | 部署 | 数据合规 | 建议 |
|------|------|------|------|---------|------|
| **本地 PaddleOCR / PP-StructureV3** | 中文高 | **零边际成本**（仅算力） | 需自建服务 | 数据不出内网 | ✅ **推荐** |
| 云厂商 OCR API | 高 | 按页计费 | 零部署 | 数据出网 | 备选/兜底 |
| 多模态大模型识图 | 最高 | 高 | 零部署 | 数据出网 | 仅高价值文档 |
| Tesseract | 中文一般 | 零 | 简单 | 安全 | ❌ 不作为主方案 |

**推荐本地 PaddleOCR 系列**，理由：PP-StructureV3 具备版面区域检测、表格识别与公式识别能力，可将 PDF/图像转为 Markdown 等结构化内容，是免费开源方案，中文场景成熟，且数据不出内网。

**部署形态**：

```
OcrService（接口）
  ├── LocalPaddleOcrService    （HTTP 调用自建 OCR 服务）
  └── CloudOcrService          （云厂商 API，兜底/对比）
```

本地 OCR 服务独立部署为 HTTP 微服务（Python + PaddleOCR），平台侧仅依赖 HTTP 契约。好处是：OCR 服务可独立扩容、可独立升级模型、不影响主应用发布节奏；同时避免把 Python 运行时塞进 Java 应用。

#### 8.2.1 先判断：到底需不需要 OCR

**这是最该先做的一步。OCR 只对"没有文本层的文档"才需要**，而大多数企业文档并不需要：

| 文档类型 | 需要 OCR？ | 原因 |
|---------|-----------|------|
| Word / Excel / PPT | ❌ 不需要 | POI 可直接提取结构化文本 |
| 有文本层的 PDF | ❌ 不需要 | PDFBox 可直接提取文字与坐标 |
| 扫描件 PDF（影印/拍照） | ✅ **需要** | 无文本层，必须识图 |
| 图片（JPG/PNG） | ✅ **需要** | 本身就是图像 |

**一句话判断方法**：打开一个 PDF，**尝试选中并复制里面的文字**。

- 能正常复制 → 有文本层 → **不需要 OCR**
- 选不中、复制出来是乱码或空 → 扫描件 → **需要 OCR**

**批量判断**：解析时统计每个文档"提取出的字符数 ÷ 页数"，
- 结果接近 0（如 <50 字符/页）→ 判定为扫描件
- 结果正常（几百字符/页）→ 有文本层

这个统计应当**由解析器自动完成**，并在索引报告中给出"扫描件占比"，作为是否部署 OCR 的决策依据（也正好回答了待确认项 U4）。

> **重要**：扫描件占比是**随客户文档而变的，设计期无法预设**。因此架构上的要求不是"要不要做 OCR"，而是**"OCR 必须随时可插拔，开启后立刻可用"**——见 8.2.3。

#### 8.2.2 本地 OCR 硬件配置要求

**核心结论：CPU 就能跑，GPU 只是加速项。** 许多资料让人误以为 OCR 必须上 GPU，实际上 PaddleOCR 在 CPU 上完全可用，只是慢一些。

**按吞吐量分三档**：

| 场景 | 日均扫描页 | CPU | 内存 | GPU | 单页耗时参考 |
|------|-----------|-----|------|-----|-------------|
| **轻量** | < 1,000 页 | 4 核 | 8 GB | **不需要** | 约 2~5 秒（CPU） |
| **标准** | 1,000 ~ 5,000 页 | 8 核 | 16 GB | 可选 | 约 1~2 秒（CPU） |
| **高吞吐** | > 5,000 页 | 8 核+ | 16 GB+ | **建议有** | < 1 秒（GPU） |

**显存需求（如使用 GPU）**：

| 模型 | 显存占用 | 适用 |
|------|---------|------|
| PP-OCRv4 / v5（纯文字检测识别） | 约 **2 GB** | 只需提取文字的场景 |
| **PP-StructureV3**（版面+表格+公式） | 约 **4 ~ 8 GB** | ✅ 推荐，能力完整 |
| 多实例并发 | 单模型显存 × 实例数 | 建议单卡不超 2 个实例 |

> **4 GB 显存的显卡即可运行 PP-StructureV3**（如 GTX 1650 / T4 级别）。门槛很低，**不必为此专门采购显卡**。

**软件环境**：

| 项 | 要求 |
|---|---|
| Python | 3.8 ~ 3.12（推荐 3.10） |
| 框架 | PaddlePaddle（CPU 版或 GPU 版）+ PaddleOCR |
| CUDA | 仅 GPU 时需要，须与 PaddlePaddle 版本对应 |
| 部署 | 独立 HTTP 微服务，Docker 化（官方提供镜像） |
| 模型体积 | PP-StructureV3 全量约 1~2 GB（首次启动自动下载，建议预置到镜像） |

**容量估算公式**（用于按实际量级定配置，而非拍脑袋）：

```
所需并发数 ≈ (日均扫描页数 × 单页处理秒数) / 86400
```

**代入示例**：

| 日均页数 | 单页耗时 | 所需并发 | 结论 |
|---------|---------|---------|------|
| 5,000 | 2 秒 | 约 0.12 | 一张消费级 GPU 绰绰有余 |
| 5,000 | 3 秒（CPU） | 约 0.17 | 单机 CPU 多进程即可 |
| 50,000 | 2 秒 | 约 1.16 | 需要 2 个实例或一张较好的卡 |

**关键洞察**：即便日均 5,000 页，所需并发也远小于 1。这意味着**绝大多数企业场景下，OCR 不是性能瓶颈，用现有服务器或一张旧卡即可**。只有当扫描件占比高且文档量极大时，才需要认真考虑扩容。

#### 8.2.3 可插拔设计（应对占比不确定）

由于扫描件占比无法在设计期确定，架构必须支持**随时启用、无需改造**：

| 设计要求 | 具体做法 |
|---------|---------|
| **默认关闭** | `app.rag.ocr.enabled=false`，不部署 OCR 服务时平台正常运行 |
| **优雅降级** | OCR 未启用时，扫描件解析为"无文本内容"并标记 `ocr_skipped`，**不报错、不阻断**其他文档 |
| **自动识别** | 解析器按 8.2.1 的方法自动判定扫描件，无需人工标注 |
| **按需启用** | 配置 endpoint 并置 `enabled=true` 即可生效，**无需重建已有索引**（仅新增文档走 OCR） |
| **可选回填** | 对已索引的扫描件，提供"重新解析"入口，启用 OCR 后可批量补做 |
| **成本可见** | 索引报告中给出"扫描件占比"与"OCR 处理页数"，让用户知道钱花在哪 |

**部署建议**：

1. **一期默认不部署**。先跑一遍现有文档，看索引报告里的扫描件占比。
2. **占比 < 10%** → 可以长期不开 OCR，或只在需要时对个别文档手动触发。
3. **占比 > 10%** → 部署本地 OCR 服务（CPU 版即可起步），无需 GPU。
4. **占比 > 50% 且量大** → 再评估 GPU 加速。

**这个顺序的价值**：它把"要不要花钱买硬件"变成了一个**由数据回答的问题**，而不是设计期的猜测。**先上线、再看数据、最后决定是否加配置**，避免为不确定的需求提前投入。

### 8.3 解析产物规范

解析结果不直接进切分器，而是先落地为**结构化中间表示**：

```json
{
  "documentId": "doc_xxx",
  "blocks": [
    { "type": "title", "level": 1, "text": "第 3 章 设备维护", "page": 12, "bbox": [..] },
    { "type": "paragraph", "text": "...", "page": 12, "bbox": [..] },
    { "type": "table", "markdown": "| a | b |\n|---|---|\n| 1 | 2 |", "page": 13 },
    { "type": "image", "ocrText": "...", "confidence": 0.94, "page": 13 }
  ],
  "meta": { "parser": "paddle-pp-structure-v3", "pages": 20, "ocrRatio": 0.6 }
}
```

这个中间层的价值：**切分策略与解析器解耦**。换解析器不影响切分逻辑，换切分策略不需要重新解析。同时 `page`/`bbox` 字段是引用溯源与命中高亮的数据基础。

## 9. 嵌入与重排模型选型

### 9.1 嵌入模型

已核实的当前价格（阿里云百炼，北京地域）：

| 模型 | 最大维度 | 价格（元/千 token） | 折合（元/百万 token） | 备注 |
|------|---------|------------------|-------------------|------|
| text-embedding-v3 | 1024 | 0.0005 | 约 0.5 | 当前 Dify 侧使用 |
| text-embedding-v4 | 2048 | 0.0005 | 约 0.5 | Batch 接口减半（约 0.25） |
| qwen3.7-text-embedding | 2560 | 0.0005 | 约 0.5 | **维度超 HNSW 上限，慎用** |
| qwen3.7-text-embedding-flash | 1024 | 0.000125 | 约 0.125 | **最便宜，轻量场景优选** |

**选型建议**：

- **默认：text-embedding-v4，1024 维**。理由：价格与 v3 相同但检索性能更强；1024 维兼顾质量、存储与 HNSW 索引性能；1024 是官方文档中标注的性价比平衡点。
- **高并发降本场景：qwen3.7-text-embedding-flash**，价格约为 v4 的四分之一，且维度上限就是 1024，正好避开超限问题。
- **明确不用 2560 维模型**，除非放弃 HNSW 改用精确检索或降维，得不偿失。
- **必须预留多模态**：平台已有 FAQ 图片（F12），二期若要让图片参与语义检索，需要多模态嵌入模型。**已核实的候选与关键结论**（阿里云百炼，北京地域）：

| 模型 | 原生维度 | 可配置维度 | 文本价（元/百万 token） | 图片价（元/百万 token） | 备注 |
|------|---------|-----------|---------------------|---------------------|------|
| `qwen3-vl-embedding` | 2560 | 2560 / 2048 / **1536 / 1024** / 768 / 512 / 256 | 0.7 | 1.8 | 质量高，但**仅 DashScope SDK/API 支持融合向量**，不支持 OpenAI 兼容接口 |
| `qwen2.5-vl-embedding` | **1024** | 2048 / **1024** / 768 / 512 | — | — | 原生即 1024，**天然落在约束内** |
| `tongyi-embedding-vision-flash` | **768** | 固定 768 | 0.15（统一计费） | 0.15（统一计费） | 低成本，但不能输出 1024 维 |
| `tongyi-embedding-vision-flash-2026-03-06` | **768** | 768 / 512 / 256 / 128 / 64 | 0.15（统一计费） | 0.15（统一计费） | 支持融合与独立向量，仍不能输出 1024 维 |
| `tongyi-embedding-vision-plus` | 1152 | 固定 1152 | 0.5（统一计费） | 0.5（统一计费） | 与带日期版本的维度能力不同 |
| `tongyi-embedding-vision-plus-2026-03-06` | 1152 | 1152 / **1024** / 512 / 256 / 128 / 64 | 0.5（统一计费） | 0.5（统一计费） | 可输出 1024 维，需锁定完整模型版本名 |

**三条关键结论**：

1. **维度约束可以通过选型或降维解决，但不能据此混合向量空间**。`qwen3-vl-embedding` 可以输出 1024 维，仍须建立独立的多模态空间；固定 768 维的 vision-flash 需要独立物理表或维度路由。相同维度只解决 PgVector 列与索引约束，不保证两个模型的向量可比较。
2. **`tongyi-embedding-vision-flash` 是成本最优解**。图片与文本统一按 0.15 元/百万 token 计费，是 `qwen3-vl-embedding` 图片价（1.8）的 **1/12**。图文混合检索的主要成本来自图片 token，这个差价不是小数。
3. **推荐策略是双空间检索**。文本切片和图片 Caption 使用文本模型；图片视觉内容及用于以文搜图的查询文本使用同一个多模态模型。两路分别召回后做排名融合。这样既控制文本成本，也保持跨模态向量的可比性。

**另需注意一个工程细节**：上图部分多模态模型（尤其 `qwen3-vl-embedding` 的融合向量模式）**仅支持 DashScope 原生 SDK 或 HTTP API**，不支持 OpenAI 兼容接口。而 Spring AI 的 OpenAI 兼容客户端是多数项目的默认接入方式。因此多模态嵌入通道**大概率需要单独实现一个 `EmbeddingModel` 适配器**（直连 DashScope HTTP），不能简单复用现有文本嵌入的客户端。这一点必须在一期设计时就预留接口，否则二期接入时会发现架构上无机可插。

### 9.2 重排模型

已核实：`qwen3-rerank` 价格 **0.5 元/百万 token**，最大输入长度 30000，**仅文本模态**（RPM 5400）。

**多模态重排（二期，图片入库后才有意义）**：

| 模型 | 文本价 | 多模态价 | 备注 |
|------|-------|---------|------|
| `qwen3-vl-rerank` | 0.5 元/百万 token | **0.5 元/百万 token** | 已于 2026-08-31 降价，**多模态与文本同价**（原为 1.8，降幅 72%） |

> **这个降价值得单独记录**：Qwen3-VL-Rerank 的多模态输入价从 1.8 降到 0.5，与文本输入同价。这意味着**图文重排不再有"多模态溢价"**——上一版的"多模态重排很贵"结论已不成立。但仍需注意：**自研侧不强制要求多模态重排模型**（见第 18 章 18.4），这是相对 Dify 的一个自由度优势。

**重排是性价比最高的质量投入**。原因：

- 向量召回是"粗筛"，重排是"精排"。典型收益是 top5 命中率提升 15~30 个百分点，成本却极低。
- 成本量级：一次重排输入 = query（约 50 token）+ N × 候选块（N=20，每块 300 token）≈ 6050 token。即**每次重排约 0.003 元**（按 0.5 元/百万 token 计算）。一万次检索约 30 元。
- 相比之下，为提升召回率而盲目扩大 topK 会导致上下文膨胀、LLM 输入成本上升，反而不划算。重排是"用便宜模型省贵模型的钱"。

**降级方案**：本地 CrossEncoder 重排（如 bge-reranker 系列），零边际成本，效果接近，但需 GPU 与维护成本。建议二期评估。

### 9.3 查询改写成本

改写使用低温度小模型，适合处理“它怎么配置”一类多轮指代查询。默认采用 AUTO：保留原查询，仅在多轮指代、短查询或歧义检测命中时产生改写查询，并将原查询与改写查询一起进入召回或对比。不能只凭“长度大于 15 字”决定跳过，也不能用改写结果完全替换原查询。

## 10. 成本模型与测算

### 10.1 成本构成

自研 RAG 相对于外挂 Dify，成本结构发生本质变化：

| 成本项 | 外挂 Dify | 自研 |
|--------|----------|------|
| 引擎许可/部署 | Dify 实例部署与运维 | 无（自建在应用内） |
| 嵌入 | 含在 Dify 内（通常 Dify 侧自带额度或另配） | **平台自付**，按 token |
| 图片嵌入（多模态） | 随 Dify 计费（图片 token 通常更贵） | **平台自付**，按图片 token（单价见 9.1，第 18 章有专项测算） |
| 检索 | 无额外费用 | 向量检索算力（含在 PG 内），**近似为零** |
| 重排 | Dify 内置 | **平台自付**，按 token |
| OCR | Dify 内置（若版本支持） | **平台自付**（本地则仅算力） |
| LLM 生成 | 平台自付 | 平台自付（不变） |
| 存储 | Dify 侧 | PG 向量存储 + 对象存储 |

**关键洞察**：自研把"黑盒外包成本"转化为"透明自付成本"。这既是风险（原本别人担的现在自己担）也是机会（可优化、可归集、可预测）。

### 10.2 测算模型

**一次性索引成本**：

```
C_index = (T_total / 1_000_000) × P_embed + P_ocr × N_ocr_pages + C_parse_compute + C_vector_build + C_storage
```

其中：
- `T_total` = 全部文档的 token 总量（含父块展开后的重复计入）
- `P_embed` = 嵌入单价（元/百万 token）
- `N_ocr_pages` = 需 OCR 的页数
- `C_parse_compute` = 解析与 OCR 所需 CPU/GPU 实例时长
- `C_vector_build` = HNSW 构建、重建、Vacuum 与副本资源
- `C_storage` = 原文件、解析产物、向量、HNSW、WAL、备份及保留版本

**每次检索成本**：

```
C_query = (T_rewrite × P_small) + (T_rerank × P_rerank) + (T_context × P_llm_in)
```

注意 `T_context × P_llm_in` **通常占总成本的 90% 以上**——检索本身很便宜，贵的是把检索结果喂给大模型。这一点决定了优化重心：**减少无效上下文比减少检索次数更重要**。

**月度成本**：

```
C_month = C_index_oneoff + C_query × Q_month + C_storage
```

### 10.3 三档规模测算

以「text-embedding-v4 @ 1024 维、qwen3-rerank、文档平均每页 500 汉字（约 750 token）」为假设：

**小规模（10 个库 / 1000 篇文档 / 平均 15 页）**

| 项目 | 计算 | 金额 |
|------|------|------|
| 总页数 | 1000 × 15 | 15,000 页 |
| 总 token | 15,000 × 750 | 11.25 M |
| 嵌入成本 | 11.25 × 0.5 元 | **约 5.6 元** |
| OCR（假设 30% 扫描件） | 4,500 页 | 本地：0 元 / 云：约 45~90 元 |
| 索引一次性合计 | | **约 6 元（本地 OCR）** |
| 月检索量 | 10,000 次 | |
| 重排成本 | 10,000 × 0.003 元 | **约 30 元/月** |
| 向量原始数据下限 | 11.25M token ÷ 750 ≈ 15,000 块 × 1024 维 × 4 字节 | **约 60 MB**，未含 HNSW、文本、元数据、WAL、备份和版本副本 |
| **月度合计** | | **约 36 元/月 + 一次性 6 元** |

**中规模（100 库 / 10,000 篇 / 平均 20 页）**

| 项目 | 计算 | 金额 |
|------|------|------|
| 总页数 | 200,000 页 | |
| 总 token | 150 M | |
| 嵌入成本 | 150 × 0.5 | **约 75 元** |
| OCR（30%） | 60,000 页 | 本地：0 元 / 云：约 600~1,200 元 |
| 向量原始数据下限 | 约 200,000 块 × 4 KB | **约 800 MB**，生产容量需通过压测乘以综合放大系数 |
| 月检索量 | 300,000 次 | |
| 重排成本 | 300,000 × 0.003 | **约 900 元/月** |
| **月度合计** | | **约 900 元/月 + 一次性约 75 元** |

**大规模（1000 库 / 100,000 篇 / 平均 25 页）**

| 项目 | 计算 | 金额 |
|------|------|------|
| 总页数 | 2,500,000 页 | |
| 总 token | 1,875 M | |
| 嵌入成本 | 1,875 × 0.5 | **约 938 元** |
| 向量原始数据下限 | 约 2.5M 块 × 4 KB | **约 10 GB**，未含索引与多版本；不能直接作为磁盘预算 |
| 月检索量 | 5,000,000 次 | |
| 重排成本 | 5,000,000 × 0.003 | **约 15,000 元/月** |
| **月度合计** | | **约 15,000 元/月 + 一次性约 938 元** |

### 10.4 成本结论与降本手段

**结论**：

1. **索引是一次性小钱**。即便 10 万篇文档，嵌入总成本不到 1000 元。**不要在嵌入上省钱而降低质量**，那是捡芝麻丢西瓜。
2. **重排是持续性的主要成本**。大规模场景月成本可达万元级，必须优化。
3. **LLM 上下文成本远超检索成本**，是真正的成本黑洞。
4. **OCR 走本地还是云，取决于扫描件占比与合规要求**。本地是零边际成本但需算力，云是零部署但按页付费且数据出网。
5. **按 1 万张图片、每张约 1000 图片 token 的假设**，总量约 10 M token：单价 0.15 元/百万 token 时约 1.5 元，单价 1.8 元/百万 token 时约 18 元。该数字只覆盖嵌入 API，不包含图片下载、Caption、失败重试、存储、索引和原图进入 LLM 上下文的费用。预算必须以真实账单和真实分辨率校准。

**降本手段（按投入产出比排序）**：

| 手段 | 节省幅度 | 实现难度 | 建议 |
|------|---------|---------|------|
| **语义缓存**（相似查询复用结果） | 重排成本 ↓30~60% | 中 | ✅ 优先 |
| **重排前截断**（只对 top20 重排，而非 top100） | 重排成本 ↓80% | 低 | ✅ 优先 |
| **嵌入 Batch 接口** | 嵌入成本 ↓50% | 低 | ✅ 索引期启用 |
| **小模型嵌入**（flash 版） | 嵌入成本 ↓75% | 低 | 按场景分级 |
| **上下文压缩**（重排后压缩冗余） | LLM 输入 ↓20~40% | 中 | ✅ 优先 |
| **分层重排**（先廉价模型粗排，再精排 top5） | 重排成本 ↓50% | 中 | 二期 |
| **本地重排模型** | 重排成本 ↓100% | 高（需 GPU） | 二期评估 |
| **TTL 缓存**（热点知识库常驻） | 视命中率 | 低 | 按需 |

**语义缓存是最高杠杆项**，值得单独说明：企业内部知识库的查询分布高度集中（同样的问题反复问）。对 query 做嵌入后查缓存，相似度超阈值（如 0.95）直接返回上次的检索结果，可跳过嵌入、检索、重排三段。**在客服场景中，缓存命中率常可达 40% 以上**，这意味着近一半的成本可直接省掉。缓存需按知识库版本隔离，版本切换时自动失效。

```properties
app.rag.ocr.provider=LOCAL                  # LOCAL | CLOUD | NONE
```

### 12.2.1 模型中心

当前“模型通道”只适合对话模型路由。自研 RAG 需要把通道与模型分开管理：一个通道保存 Base URL、加密密钥、超时和重试；一个通道可以注册多个不同能力的模型。模型目录至少支持以下能力类型：

| 能力类型 | 用途 | 关键元数据 |
|---------|------|-----------|
| CHAT | Agent 对话、查询改写 | 上下文长度、Vision 能力、价格 |
| TEXT_EMBEDDING | 文本切片、图片 Caption 向量化 | 维度、可选维度、批量上限、向量空间 |
| MULTIMODAL_EMBEDDING | 图片向量、以文搜图、以图搜图 | 支持模态、维度、融合/独立向量模式 |
| RERANK | 文本候选精排 | 最大输入、价格 |
| MULTIMODAL_RERANK | 图文候选精排 | 支持模态、图片限制 |
| VISION_CAPTION | 为图片生成描述 | 输入限制、输出预算、价格 |

模型目录由后端返回，不允许前端硬编码。每条模型记录包含稳定 `modelId`、完整模型版本、`providerId`、能力标签、维度、地域、单价、健康状态和是否允许新建索引。知识库页面只引用模型 ID，不接触 API Key。

### 12.5 核心交互三：检索调试台

这是**最能体现实力差异的 UI**，现有版本完全缺失。目标是让"检索为什么不准"变成可定位、可复现的问题。

**必须实现的关键能力**：

1. **参数改动即时生效并重跑**：调滑块就能看到结果变化，这是从"猜"到"看"的关键。
2. **分段耗时与漏斗图**：能看出瓶颈在哪一段。
3. **每一步的数量变化**：20 → 20 → 24 → 5 → 4，一眼看出是召回不足还是重排误杀。

6. **对比模式**：宽屏时左右展示两个引擎或版本；窄屏切换结果 Tab，并固定显示差异摘要。
7. **分数语义明确**：展示原始距离、归一化分或排名时必须标注类型。RRF 分数不显示为相关概率，跨模型原始分数不直接横向比较。

## 13. 知识库管理能力设计（库级配置与召回测试）

> 前一章（12）解决的是"引擎怎么选、版本怎么切"的架构层交互；本章解决的是**知识库作为一个产品实体，自身该有的管理能力**。
> 这一章是硬要求：自研知识库必须在**库级配置**与**召回测试**两条线上与 Dify 完全对等，否则用户没有任何理由从 Dify 迁过来——因为迁移的收益是"更可控"，而前提是"可控的东西得看得见、改得动、验得了"。

### 13.1 现状核查：已有什么、缺什么

先厘清现状，避免重复建设。核查结论如下：

| 能力项 | 数据库字段 | 后端 DTO | UI 表单 | 结论 |
|--------|-----------|---------|---------|------|
| 名称 | `name` ✅ | ✅ | ✅ | 完整 |
| 图标/头像 | `avatar`（默认 📚）✅ | ✅ | ✅ 有 emoji 选择器 | 完整，但仅 emoji |
| 描述 | `description` ✅ | ✅ | ✅ | 完整 |
| 可见权限 | `permission`（`only_me` 等）✅ | 仅**创建 DTO** 可传 | ❌ 当前弹窗无控件、提交时也未传 | ⚠️ 实际依赖后端默认值，创建后不可改 |
| 索引模式 | `indexing_technique`（`high_quality`）✅ | 仅**创建 DTO** 可传 | ❌ 当前弹窗无控件、提交时也未传 | ⚠️ 实际依赖后端默认值，创建后不可改 |
| 嵌入模型 | `embedding_model` / `embedding_provider` ✅ | 仅**创建**时可传 | 固定展示并提交 `text-embedding-v3`，无选择器 | ⚠️ 看似配置，实际不可选、不可改 |
| 检索方式 | `search_method` ✅ | ✅ 可更新 | ✅ 三卡片（向量/全文/混合） | 完整 |
| TopK | `top_k` ✅ | ✅ 可更新 | ✅ 滑块 | 完整 |
| 重排开关/模式 | `rerank_enabled` / `rerank_mode` ✅ | ✅ 可更新 | ✅ | 完整 |
| 重排模型 | `rerank_model` ✅ | ✅ 可更新 | 展示但不可选 | ⚠️ 需要模型目录驱动的选择器 |
| 多模态模型与配置 | ❌ | ❌ | ❌ | ⚠️ 文档有方案，代码尚未实现 |
| 权重 | `vector_weight` / `keyword_weight` ✅ | ✅ 可更新 | ✅ 双滑块联动 | 完整 |
| **召回测试** | — | ❌ 无端点 | ❌ **无入口** | ⚠️ **完全缺失**（见 13.5） |
| 文档/FAQ 管理 | ✅ | ✅ | ✅ | 完整 |

**核心结论（三条）**：

1. **数据层只覆盖现有 Dify 文本检索配置**。`knowledge_bases` 已有 `indexing_technique`、`embedding_model`、`search_method` 等字段，但索引版本、模型版本、维度、向量空间、多模态设置和 Caption 配置仍需新增表或版本配置 JSON，不能得出“不需要加字段”的结论。
2. **断裂在 DTO 与 UI 层**——`UpdateKnowledgeBaseRequest` 相比 `CreateKnowledgeBaseRequest` **少了 `permission`、`indexingTechnique`、`embeddingModel`、`embeddingProvider`、`provider` 五个字段**。这意味着这些配置**创建时能设、之后永远改不了**，用户一旦选错只能重建知识库——这是必须修的产品级缺陷。
3. **召回测试完全缺失**——既无后端端点也无 UI，用户配完参数无法验证效果，只能靠"去 Agent 里问一句试试"，这是自研相对 Dify 最大的体验落差。

### 13.2 知识库设置面板：完整能力矩阵

统一到知识库详情的“设置”Tab，替代现有的“编辑信息”大弹窗。设置按变更代价分组；索引配置的修改进入新建版本向导，不直接更新当前版本。

```
知识库设置
├── ① 基础信息
│     ├── 名称 *              文本，1~200 字符，库内唯一
│     ├── 图标                  emoji 选择器 + 自定义上传（见 13.3）
│     ├── 描述                 多行文本，≤500 字符，支持 Markdown
│     └── 可见权限             only_me / all_team_members / partial_members
│
├── ② 索引配置（⚠️ 仅新索引版本生效）
│     ├── 索引模式             HIGH_QUALITY（高质量） / ECONOMY（经济）
│     ├── 文本嵌入模型          模型选择器（按引擎与能力过滤，见 13.4）
│     ├── 多模态嵌入模型        可选，启用图文检索时展示
│     └── 分块模式             自动 / 自定义（自定义时展开块大小、重叠、分隔符）
│
├── ③ 检索设置（✅ 即时生效，无需重建索引）
│     ├── 检索方式             ⦿ 向量检索  ○ 全文检索  ○ 混合检索
│     ├── TopK                 滑块 1~20，默认 3
│     ├── 分数阈值              滑块 0~1，可关闭，默认关
│     └── 融合与重排（仅混合检索时展开）
│           ├── 融合方式        ⦿ 权重设置（默认，无需 Rerank API）  ○ 重排序模型
│           ├── 权重            语义 vs 关键词双滑块联动（默认 0.7 / 0.3）
│           └── 重排模型        qwen3-rerank（默认关闭，开启时需选模型，见 13.4）
│
├── ④ 多模态配置（仅多模态版本显示）
│     ├── 图片来源、Caption 模型、图片上下文策略
│     └── 多模态 Rerank 与历史图片回填状态
│

      ├── 启用/停用开关
      └── 删除知识库（二次确认 + 输入库名）
```

> **注意"权重设置"与"重排序模型"是互斥的融合方式**，与 Dify 一致：混合检索下二选一即可。**默认走"权重设置"，不需要任何 Rerank 模型 API 与 Token 消耗**——这是成本最优的默认路径。仅当评测显示"召回对了但排序不佳"时才切换到"重排序模型"（判据见 7.4）。

**关键设计原则——"改动的代价必须提前说清"**：

设置面板里，**② 索引配置**与 **③ 检索设置**必须用视觉区分，因为它们对用户的意义完全不同：

| 分组 | 改动后果 | 生效方式 | UI 表现 |
|------|---------|---------|---------|
| ① 基础信息 | 无副作用 | 即时 | 普通表单 |
| ② 索引配置 | **需要重建索引**（耗时、花钱） | 生成新索引版本 | 橙色警示条 + 预计成本/耗时 |
| ③ 检索设置 | 无副作用，仅影响后续检索 | 即时 | 普通表单 + 绿色"即时生效"标识 |

具体到 ②，当用户修改索引模式或嵌入模型时，**不允许原地保存**，而是弹出引导：

```
┌──────────────────────────────────────────────────────┐
│  ⚠️ 该修改需要重建索引                                  │
│                                                      │
│  你修改了「嵌入模型」：                                  │
│    text-embedding-v3  →  text-embedding-v4            │
│                                                      │
│  维度与模型变更后，已有向量全部失效，必须重建。             │
│  不会影响当前线上检索（仍使用 v2 版本），                  │
│  重建完成后由你确认是否切换。                              │
│                                                      │
│  预计：128 篇文档 · 约 3 分钟 · 嵌入成本约 ¥2.4            │
│                                                      │
│  ☐ 我已了解，创建新索引版本                             │
│                                                      │
│            [取消]   [创建索引版本并重建]                 │
└──────────────────────────────────────────────────────┘
```

**这就是第 5 章"索引版本"抽象在此处的兑现**：用户视角是"改了个设置"，系统视角是"自动新建一个索引版本并后台重建"，两条链路自然衔接，用户不需要理解"版本"这个概念，但享受了"不影响线上 + 可回滚"的好处。

### 13.3 可见权限（完善现有实现）

现状：`permission` 字段存在，但**只在创建时能设**，创建后无法修改——这是明确的缺陷。同时现有取值需要与平台的共享授权模型对齐。

| 取值 | 语义 | 谁能检索 |
|------|------|---------|
| `only_me` | 仅自己 | 所有者 + 被显式共享者 |
| `all_team_members` | 全体成员 | 所有登录用户的 Agent 均可绑定 |
| `partial_members` | 指定成员 | 所有者 + 被授权成员 |

**要点**：

1. **权限变更必须即时生效且可审计**。与第 15 章的权限继承原则一致：`permission` 是"入库级"的粗粒度开关，现有的 `VIEW`/`USE` 共享授权是"细粒度补充"，两者是"或"的关系而非替代。
2. **权限收紧时的连带处理**：从 `all_team_members` 改为 `only_me` 时，若已有他人的 Agent 绑定了该库，必须给出**影响面提示**：
   ```
   ⚠️ 有 3 个 Agent 正在使用此知识库，权限收紧后这些 Agent 将检索不到内容：
      · 客服助手（张三）
      · 售前机器人（李四）
      · 内部问答（你）
   ```
   而不是静默生效、等用户发现问题。
3. **`partial_members` 需要一个成员选择器**，复用现有的共享授权 UI 组件。

### 13.4 索引模式与嵌入模型选择

**（1）索引模式**

对齐 Dify 的两档设计，并明确其对自研引擎的实际含义：

| 模式 | Dify 侧语义 | 自研侧实现 | 适用场景 |
|------|-----------|-----------|---------|
| **高质量（HIGH_QUALITY）** | 调用嵌入模型生成向量，语义检索 | 向量化 + HNSW 索引 | 默认，语义理解要求高 |
| **经济（ECONOMY）** | 不生成向量，仅关键词索引 | 仅建全文索引（`pg_trgm` / `tsvector`），**不产生嵌入成本** | 大文档量、纯关键词匹配够用的场景 |

**经济模式的价值被低估了**：它是**零嵌入成本**的检索方案。对于"内部规范文档、条款编号检索"这类关键词就能搞定的场景，经济模式能把索引成本从"按 token 计费"直接降到零。这是自研相对 Dify 的一个隐性优势——**因为自研知道自己的检索实现，可以精确控制成本**。

**（2）嵌入模型选择器**

现状 UI 把嵌入模型写死为 `text-embedding-v3`。选择器的数据必须来自平台模型中心，而不是在 Vue 文件中维护静态列表。选择器设计要求：

| 展示项 | 说明 |
|--------|------|
| 模型名 | text-embedding-v3 / v4 / qwen3.7-text-embedding-flash |
| 维度 | 1024 / 1024 / 1024（**必须标注，且硬约束 ≤1024**） |
| 单价 | ¥0.0005 / 1k token 等，帮用户建立成本意识 |
| 能力标签 | "检索性能更强" / "最便宜，成本约 1/4" |
| 能力标签 | TEXT、VISION、FUSION、BATCH；多模态模型显示 Vision 徽标 |
| 向量空间 | 文本空间或多模态空间；模型版本变化时空间随之变化 |
| 通道状态 | 正常、降级、不可用；不可用模型禁止新建版本 |

**联动约束（必须在前端就拦住，不能等后端报错）**：

1. **物理表能力约束**：选择器按后端返回的受支持维度展示，不把“≤1024”写死在前端。模型原生维度、可配置维度和目标物理表必须兼容；不兼容项置灰并展示具体原因。
2. **引擎联动**：选择"外挂 Dify 引擎"时，嵌入模型由 Dify 侧决定，此选择器应**置灰并提示"外挂引擎的嵌入模型由 Dify 实例配置决定"**。这一条很重要——避免用户以为选了就生效。
3. **已有文档时切换 = 必须重建**：库内已有文档时修改嵌入模型，触发 13.2 的重建引导弹窗。
4. **多模态模型必须标注能力差异**：文本模型下图片只通过 Caption 或附件返回；多模态模型下图片可以进入视觉向量空间。页面必须说明查询文本是否由同一个多模态模型编码，不能只显示 Vision 徽标。
5. **Dify 配置只读**：平台展示从 Dify 获取到的模型和索引模式，不允许在本地选择一个模型却没有真正下发。

**（3）图文检索配置（多模态模型选中后展开）**

```
└── 多模态检索（仅当索引版本启用多模态空间时显示）
      ├── 图片来源        ☑ 本库上传的 FAQ 图片   ☑ 文档内嵌图片
      ├── 多模态嵌入模型  qwen3-vl-embedding（查询文本与图片使用同一空间）
      ├── 是否生成图片描述  ⦿ 是（推荐，让图片可用文字搜到）
│                     ○ 否（仅多模态向量，省 VLM 调用费）
      ├── Caption 模型     qwen-vl-plus（可选）
      ├── 单块最多图片数    10（与 Dify 对齐）
      └── ☐ 回答时附带原图（Token 消耗高，默认关闭）
```

生成 VLM 描述后，Caption 使用文本 Embedding 模型进入文本空间，可被语义和关键词召回；原图使用多模态 Embedding 模型进入多模态空间。两路结果通过排名融合合并，不能把 Caption 的文本向量与图片视觉向量直接存入同一个 HNSW 索引进行距离比较。

**重排模型选择器**同理：展示 `qwen3-rerank`（¥0.5/百万 token，单次约 ¥0.003），并预留"本地重排模型"选项（二期）。**图文检索场景下需额外说明**：自研**不强制**要求重排模型也是多模态（Dify 有此限制），若使用纯文本重排，图片不会被剔除，只是不参与排序打分——详见 18.4。

### 13.5 召回测试（Retrieval Test）——最关键的缺失能力

**这是本章的重点，也是自研知识库相对 Dify 最大的体验缺口。**

现状：知识库配置完检索参数后，**没有任何方式验证效果**。用户唯一的手段是去 Agent 里绑定这个库、然后问一句话、看回答对不对——这是**间接的、被污染的、不可复现的**验证方式（回答还受 LLM 和提示词影响，你根本不知道是检索错了还是生成错了）。

**召回测试的价值：把"检索质量"从"生成结果"中剥离出来，单独观测。**

设计为知识库详情页的一个独立 Tab，核心是**"输入查询 → 直接看召回了什么"**，不经过任何 LLM：

```
┌──────────────────────────────────────────────────────────────────┐
│  召回测试                                          [保存为评测用例]  │
├──────────────────────────────────────────────────────────────────┤
│  ┌────────────────────────────────────────────────────────────┐  │
│  │ 请输入测试查询，如：设备维护周期是多久？            [测试]   │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                  │
│  检索方式： ⦿ 混合检索  ○ 向量检索  ○ 全文检索   [使用当前配置 ▾]  │
│  TopK: 5   分数阈值: 0.25（开）   重排: 关                        │
│                                          ↑ 调试用临时值，不改库配置 │
├──────────────────────────────────────────────────────────────────┤
│  召回结果（4 条）                              耗时 415ms · ¥0.0031│
│                                                                  │
│  ┌── #1 ──────────────────────── 融合分 0.91 ──────────────────┐ │
│  │ 来源：设备维护手册.pdf  ·  第 12 页                          │ │
│  │ 向量分 0.88 ｜ 关键词分 0.76 ｜ 重排分 0.94                   │ │
│  │                                                             │ │
│  │ 「...设备需每 500 小时进行一次维护，主要包括更换滤芯、          │ │
│  │   检查油位、清洁散热片...」                                  │ │
│  │                                                             │ │
│  │ [查看原文]  [高亮命中片段]  [为什么召回这条？]                 │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                                                                  │
│  ┌── #2 ──────────────────────── 融合分 0.85 ──────────────────┐ │
│  │ 来源：维护规程.docx  ·  第 3 页                              │ │
│  │ ...                                                         │ │
│  └─────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
```

**必须实现的关键能力（按重要性排序）**：

| 能力 | 说明 | 为什么重要 |
|------|------|-----------|
| **直接展示切片原文** | 不做任何摘要或改写，原样展示召回到的切片 | 用户能一眼判断"召回得对不对" |
| **展示分数构成** | 向量分 / 关键词分 / 融合分 / 重排分 分列 | 能定位是"召回阶段就错了"还是"重排误杀了" |
| **临时覆盖参数** | 面板上的 TopK / 阈值 / 检索方式仅在本次测试生效，**不改动库配置** | 让用户可以放心试参数，试好了再回设置里保存 |
| **来源与页码** | 文档名 + 页码 + 原文位置 | 判断依据是否可靠（依赖第 7 章的 `pageNo`/`bbox` 增强） |
| **分段耗时与成本** | 本次测试的耗时与费用 | 建立成本感知 |
| **保存为评测用例** | 一键把当前查询 + 期望命中的文档存为评测集条目 | **让调优过程沉淀为回归资产**（衔接质量门禁，见后文评测章） |
| **空结果的可诊断提示** | 召回为空时，不能只显示"无结果" | 见下文 |
| **图片结果缩略展示** | 命中带图片的切片时，**必须在结果卡片里直接显示图片缩略图**，而不是只显示路径或文件名 | 图文检索下"召回得对不对"很大程度要靠眼睛判断；只给文字等于让用户猜 |

**空结果的处理——这是最能体现产品成熟度的细节**：

召回为空时，用户最想知道的是"为什么"。面板不能只显示一片空白，而应给出**分层诊断提示**：

```
未召回任何结果

可能原因（按概率排序）：
  · 分数阈值过高（当前 0.25）—— 有 3 条候选因低于阈值被过滤  [临时关闭阈值重试]
  · 知识库内可能确实没有相关内容 —— 建议换一个说法或确认文档已索引
  · 全文检索未命中关键词 —— 该查询的专有名词可能分词失败  [切换为向量检索重试]
```

**每一条提示都带一个"一键重试"动作**，让用户能立刻验证猜测。这比给一堆错误码有用得多——**诊断的价值在于给出可执行的下一步，而不在于解释原因**。

**与调试台的关系**：第 12 章 12.5 的"检索调试台"面向**管理员/工程师**，三栏布局、可视化召回漏斗、可做双引擎对比；本节的"召回测试"面向**知识库所有者（普通用户）**，单栏、简洁、聚焦"我这个库配得对不对"。**两者共用同一套后端检索端点**，只是前端复杂度和受众不同。这是有意的分层，不要合并。

### 13.6 后端接口补齐

现有端点：`GET /{id}`、`POST`、`PUT /{id}`、`DELETE /{id}`、`POST /sync-from-dify`、文档与 FAQ 相关端点。

**需要补齐的部分**：

| 接口 | 用途 | 备注 |
|------|------|------|
| `PUT /{id}` **扩展** | 支持基础信息、权限和即时检索设置 | Embedding、维度、解析与分块配置禁止通过此接口原地修改 |
| `POST /{id}/index-versions` | 按选定引擎、模型、维度、解析和分块配置创建新版本 | 索引配置不再通过普通 PUT 原地修改 |
| `GET /{id}/index-versions` | 版本列表、进度、校验结果和发布状态 | 支撑版本 Tab |
| `POST /{id}/index-versions/{versionId}/publish` | 原子切换主流量指针 | 仅 READY 可发布 |
| `POST /{id}/index-versions/{versionId}/retry` | 使用相同配置重试失败任务 | 调整配置必须新建版本 |
| `POST /{id}/retrieval-test` | **召回测试**（新增，核心） | 见下方契约 |
| `POST /{id}/retrieval-test/save-case` | 保存为评测用例 | 衔接评测集 |
| `GET /api/model-catalog?capability=...` | 平台模型目录，返回维度、价格、模态、版本和通道状态 | Embedding、Rerank、Caption 选择器统一消费 |
| `PUT /{id}/multimodal-settings` | **图文检索配置**（图片来源、是否生成描述、单块图片数上限） | 仅多模态库可见（见第 18 章） |
| `POST /{id}/images/{imageId}/reembed` | **对已入库图片补做向量化** | 从文本模型切到多模态模型后，历史图片需回填 |

**召回测试接口契约**（新增）：

```json
// POST /api/knowledge-bases/{id}/retrieval-test
{
  "query": "设备维护周期是多久？",
  "queryImageId": null,            // 可选：以图搜图时传入图片 ID
  "override": {                    // 可选，仅本次生效，不写库
    "indexVersionId": "kiv_03",
    "searchMethod": "hybrid_search",
    "topK": 5,
    "scoreThreshold": 0.25,
    "rerankEnabled": false,
    "vectorWeight": 0.7
  }
}
```

响应：

```json
{
  "chunks": [
    {
      "chunkId": "c_8812",
      "documentId": "doc_17",
      "documentName": "设备维护手册.pdf",
      "pageNo": 12,
      "content": "...设备需每 500 小时进行一次维护...",
      "images": [                // 新增：该切片携带的图片（无图则为空数组）
        {
          "imageId": "img_31",
          "url": "/api/knowledge-bases/{id}/images/img_31",  // 受控下载，非静态暴露（修正 F12）
          "caption": "设备维护周期示意图，标注 500 小时节点",       // 生成的图片描述（若开启）
          "vectorScore": 0.86,   // 图片向量分（多模态模型下才有）
          "matchedBy": "IMAGE_VECTOR"   // IMAGE_VECTOR（图片向量命中）| TEXT_ONLY（文本侧命中）
        }
      ],
      "vectorScore": 0.88,
      "keywordScore": 0.76,
      "fusedScore": 0.91,
      "rerankScore": 0.94,
      "scoreType": "NORMALIZED_COSINE",
      "rank": 1,
      "vectorSpace": "TEXT:text-embedding-v4@2026-08",
      "tokenCount": 186
    }
  ],
  "filteredOut": 3,              // 被阈值过滤掉的候选数（用于诊断提示）
  "stageTimings": { "rewrite": 120, "recall": 85, "rerank": 210, "total": 415 },
  "cost": { "total": 0.0031, "rerank": 0.0031, "imageEmbedding": 0.0002 },
  "engineResolution": { "effectiveEngine": "SPRING_AI", "source": "KB_BINDING" }
}
```

响应中的分数必须同时返回 `scoreType`、`rank` 和 `vectorSpace`。跨引擎对比默认比较排名与命中集合；只有经过同一评测集校准的归一化分数才允许直接比较。

**`images[].matchedBy` 字段是图文检索诊断的关键**：

- `IMAGE_VECTOR` —— 该图**自身**被向量命中（查询语义匹配到了图片内容，属于真正的跨模态召回）
- `TEXT_ONLY` —— 图片只是**跟着命中切片返回**，图片本身没有参与匹配（等价于"以附件形式返回"）

这个区分让用户能一眼看出"图片参与检索了没有"，是排查"为什么搜不到那张图"的第一手依据。**没有这个字段，用户无法区分"多模态功能没生效"和"图片确实不相关"。**

**注意 `filteredOut` 字段**——它是 13.5 空结果诊断提示的数据基础。**让后端把"被过滤掉几条"告诉前端，前端才能给出有价值的诊断**，这是接口设计上容易被忽略但对体验影响很大的一点。

**复用现有接线**：Service 层已有 `KnowledgeBaseService.retrieveChunks(String kbId, String query, int topK)`（第 277 行），召回测试端点应在此基础上扩展参数与返回结构，而不是另起一套。

### 13.7 与既有设计的关系

本章不是独立的部分，它与前面各章有明确的依赖与承接关系：

| 本章能力 | 依赖/衔接 | 说明 |
|---------|----------|------|
| 索引模式、嵌入模型改动 | 第 5 章 索引版本 | 改配置 = 建新版本，不原地修改 |
| 召回测试的分数构成 | 第 7 章 7.5 检索证据对象 | 需要 `RetrievedChunk` 扩展后的多分数字段 |
| 召回测试的页码定位 | 第 8 章 解析产物规范 | 需要解析中间层保留 `page`/`bbox` |

**一句话总结本章**：知识库管理能力是"自研引擎可被接受"的入场券。引擎再强，如果用户看不见召回结果、改不了嵌入模型、调完参数没法验证，那这个自研知识库在产品上就是不完整的。**本章补的不是功能，而是"可控性"这件事本身。**

## 14. 质量门禁与评测体系

### 14.1 冻结评测集

没有评测集，"强于 Dify"就是空话。评测集设计：

| 维度 | 内容 | 规模建议 |
|------|------|---------|
| 单跳事实型 | 答案在单个切片中 | 每库 30 条 |
| 多跳推理型 | 需跨文档/跨块组合 | 每库 15 条 |
| 长文定位型 | 答案需在长文档中定位 | 每库 15 条 |
| 表格型 | 答案在表格中 | 每库 10 条 |
| 图文型 | 答案在图片/扫描件中 | 每库 10 条 |
| 拒答型 | 知识库中无答案，应明确拒答 | 每库 10 条 |
| 对抗型 | 易混淆的相似概念 | 每库 10 条 |

每条包含：`query`、`expectedDocumentIds`、`expectedAnswerPoints`（要点列表）、`difficulty`、`type`。

**评测集本身要有版本**，且一旦用于验收即冻结，不得在对比后修改——否则指标失去意义。

### 14.2 检索与生成指标

检索与生成必须分层评估。检索集应标注期望 chunk 或证据区间，而不只标注文档 ID；同一文档中可能只有一个相关块，文档级命中会掩盖切分与排序问题。

| 层级 | 指标 | 定义 | 目标 |
|------|------|------|------|
| 检索 | **Hit@5 / Recall@10** | 期望证据块是否进入前 K | ≥ 当前基线 |
| 检索 | **MRR / NDCG@10** | 首个正确证据排名与分级相关性 | ≥ 当前基线 |
| 检索 | **Evidence Precision@K** | 前 K 中真正支持答案的证据比例 | ≥ 当前基线 |
| 检索 | **检索延迟 P50/P95** | 不包含生成模型的检索端到端耗时 | P95 ≤ 基线 × 1.2 |
| 生成 | **引用准确率 / 引用覆盖率** | 引用是否支持对应结论、关键结论是否有引用 | ≥ 冻结目标 |
| 生成 | **答案忠实度** | 回答是否只使用证据支持的信息 | ≥ 冻结目标 |
| 生成 | **拒答准确率** | 无答案时正确拒答 | ≥ 0.90 |
| 生成 | **首字延迟 P95** | 检索加生成到首个 token 的耗时 | 单独报告，不代替检索延迟 |

每次对比记录样本量、模型版本、索引配置和重复运行次数。差异较小时给出置信区间，避免用一次随机运行决定发布。

### 14.3 上线门禁（硬性）

新版本发布必须同时满足：

```
□ Hit@5     ≥ 当前主流量版本
□ Recall@10 ≥ 当前主流量版本
□ NDCG@10   ≥ 当前主流量版本
□ Evidence Precision@K ≥ 当前主流量版本
□ 拒答准确率 ≥ 0.90
□ P95 延迟  ≤ 当前版本 × 1.2
□ 无严重回归用例（任何标记 CRITICAL 的用例失败即阻断）
□ 评测样本量达到平台通用集 100 条；库级小样本必须覆盖全部高风险用例
□ 成本增幅 ≤ 50%（超出需管理员显式豁免）
```

**未通过则按钮置灰，并展示具体未达标项与差距值**。门禁不可绕过，只有超级管理员可申请豁免，且豁免需填写理由并写入审计日志。

### 14.4 持续评测

- **定时回归**：每周自动跑一次全量评测，指标下降超 5% 触发告警。
- **在线指标**：收集用户对回答的反馈（现有 `user_feedback` 字段可复用），统计"有帮助率"。
- **漂移监测**：监控文档增量对指标的影响，避免"库越加越大、效果越来越差"。

## 15. 权限、审计与开放平台

### 15.1 权限继承（不可放宽）

自研引擎必须完整继承现有权限模型，且**不得引入旁路**：

| 现有机制 | 自研引擎的要求 |
|---------|--------------|
| 资源所有权（owner） | 索引版本归属知识库，间接归属 owner |
| 共享授权 VIEW / USE | 检索前校验，无 USE 权限拒绝 |
| 用户状态（DISABLED） | 所有者被禁用则其库不可被检索（现有设计原则） |
| 父子资源校验 | 文档必须属于该知识库，检索结果不得跨库泄漏 |
| 审计 | 索引版本创建/发布/回滚、引擎切换、检索调试均记审计事件 |

### 15.2 新增审计事件

```
KB_INDEX_VERSION_CREATED    创建索引版本
KB_INDEX_VERSION_PUBLISHED  发布索引版本（含切换前后引擎）
KB_INDEX_VERSION_ROLLED_BACK 回滚
KB_ENGINE_CHANGED           修改知识库引擎绑定
KB_RETRIEVAL_DEBUGGED       执行检索调试（含查询内容，需脱敏策略）
KB_COST_EXPORTED            导出成本报告
RAG_ENGINE_DEFAULT_CHANGED  修改平台默认引擎
```

### 15.3 开放平台契约

现有 `POST /open/v1/knowledge-bases/{id}/retrieve` 需扩展（保持向后兼容）：

## 18. 图文跨模态检索（多模态 RAG）

> 本章回答一个具体问题：**自研 RAG 能不能做图文？Dify 是不是不支持？**
>
> 先给结论，再给设计。

### 18.1 先纠正一个前提：Dify 是支持的，但代价不低

Dify 从 **v1.11.0** 起已正式支持多模态知识库（官方博客 2026-01-07 发布，v1.11.1 进一步完善），能力包括：**文本与图片进入统一语义空间**，实现"以文搜图、以图搜文、以图搜图"。所以"**Dify 的 RAG 不支持图文**"这个说法——**在 v1.11 之前是事实，之后已经不成立**。设计时必须以现实为前提，否则会基于错误假设做决策。

但 Dify 的实现附带**四个硬约束**（均已核实官方文档）：

| 约束 | 内容 | 影响 |
|------|------|------|
| **索引模式** | **仅"高质量（high_quality）"支持图片向量化** | 经济模式完全用不了图文检索 |
| **重排模型** | **必须是多模态（Vision）模型**，否则检索到的图片会被**从重排序和最终结果中剔除** | 强制用户在重排上也付费，即便只想用权重融合 |
| **图片限制** | 单图 ≤2MB、每 chunk ≤10 张、仅支持 JPG/JPEG/PNG/GIF | 大图、GIF 之外的格式直接忽略 |
| **上下文成本** | 图片进上下文按分辨率消耗约 100~1000 token，Top K 需相应下调 | 成本与上下文窗口双重压力 |

**第四条尤其值得注意**：Dify 可以在 Vision LLM 节点中消费检索图片，但是否把图片交给模型是可选配置。只要原图进入生成模型，上下文就会产生图片 token 并挤占预算；对比时必须使用相同的图片注入策略。

### 18.2 自研方案：双描述与双向量空间

自研不做"Dify 的翻版"，而是用一套**成本更优、可控性更高**的组合。核心是三层：

```
图片来源：FAQ 图片 / 文档内嵌图片
    │
    ├── Caption 路径
    │     VLM 生成图片描述
    │       → 与普通文本使用同一个 TEXT_EMBEDDING 模型
    │       → 文本向量召回 + 中文关键词召回
    │
    └── 视觉路径
          图片由 MULTIMODAL_EMBEDDING 模型编码
          查询文本或查询图片由同一个模型编码
            → 多模态向量召回

文本召回排名 + 多模态召回排名
    → RRF / 经评测校准的融合
    → 可选多模态 Rerank
    → 统一证据结果
```

**为什么"双描述"是关键设计？**

纯多模态向量方案（Dify 的做法）有一个隐含缺陷：**图片向量只对"视觉语义"敏感，对"文字语义"天然弱**。用户问"那个画着红色警告标志的接线图在哪"，视觉向量能命中；但问"安全操作规程里提到的接线注意事项"，视觉向量几乎无能为力——因为图片里可能根本没有"注意事项"这四个字。

双描述方案下，图片同时拥有：
- **视觉向量** —— 应对"看着像"的查询
- **描述文本**（经普通文本嵌入） —— 应对"说着像"的查询，且**能被 pg_trgm 关键词检索命中**（纯视觉向量做不到这一点）

两个空间不直接比较距离。它们复用同一套检索编排、证据对象、权限、成本和评测框架，但各自拥有物理向量表或索引。这样既保留 Caption 的文字检索能力，也保证以文搜图和以图搜图使用经过对齐的多模态向量空间。

### 18.3 三个必须解决的技术细节

**（1）维度与向量空间问题**

多模态模型原生维度普遍很宽（`qwen3-vl-embedding` 为 2560），超出 pgvector HNSW 的 2000 维上限。但这不是死结，有两条路：

| 路径 | 做法 | 评价 |
|------|------|------|
| **A. 独立 1024 多模态空间**（推荐） | `qwen3-vl-embedding` 输出 1024 维，单独建立多模态 HNSW | 与文本表规格一致但索引隔离，运维简单 |
| **B. 独立 768/1152 空间** | 使用固定维度 Vision 模型，路由到对应物理表 | 成本可能更低，但增加表与索引规格 |
| C. halfvec 半精度 | pgvector 0.7+ 可索引更宽向量 | 仅在专项评测证明宽向量有收益时采用 |

维度相同只表示可以使用相同表结构，不表示不同模型的向量可以进入同一个索引。多模态一期优先使用独立的 1024 维空间；是否采用 768、1152 或 halfvec 由专项评测决定。

**（2）接口问题——需要单独适配器**

`qwen3-vl-embedding` 的**融合向量与独立向量模式均仅支持 DashScope SDK 或原生 HTTP API，不支持 OpenAI 兼容接口**。而 Spring AI 项目默认走 OpenAI 兼容客户端。因此：

- 必须实现一个独立的 `MultimodalEmbeddingModel` 适配器，直连 DashScope；
- 该适配器**应在能力槽位体系中与文本 `Embedder` 平级**（第 4.2 节的"能力槽位"设计在此兑现——新增一个槽位实现即可，不影响其他四个）；
- 接口必须允许"一次调用同时返回图像向量"或"返回图像 + 描述分离结果"，不能假设与文本嵌入同构。

**（3）原图是否进 LLM 上下文——默认不进**

这是自研与 Dify 最大的行为差异，也是**成本差异的主要来源**：

| 策略 | 做法 | 成本 | 适用 |
|------|------|------|------|
| **Dify Vision 路径** | 开启 Vision 后，检索图片交给 Vision LLM | 图片 token 随分辨率和 Top K 增长 | 需要 LLM"看图说话"（如"这张图里的第一步是什么"） |
| **自研默认路径** | 检索到图片 → **只返回图片 URL 作为引用来源**，LLM 读文字描述 | 接近零 | 大多数检索问答场景 |
| **自研按需路径** | 用户/调用方显式开启 `inject-images-to-llm` | 同 Dify | 明确需要视觉推理时 |

**为什么默认不进**：绝大多数"图文知识库"的实际用法是——**用户想找到那张图，而不是让 LLM 描述那张图**。LLM 读了描述文本就足以回答"这个设备怎么维护"，把原图塞进上下文纯属浪费。**把"是否看图"变成调用方的显式选择，而不是框架的默认行为，这是自研应有的克制。**

### 18.4 重排：自研不强制多模态（相对 Dify 的自由度优势）

Dify 的约束是硬的：多模态知识库必须配多模态 Rerank 模型，**否则图片会被直接剥离**。

自研**不沿用这个限制**。理由是——**"图片不参与重排打分"与"图片被删除"是两件完全不同的事**：

| 做法 | 结果 | 自研选择 |
|------|------|---------|
| 纯文本重排 + 图片随切片返回 | 文本按重排分排序；图片作为切片的附属内容一并返回，**只是自身不参与打分** | ✅ **默认行为** |
| 多模态重排（`qwen3-vl-rerank`） | 文本与图片一起参与排序打分，排序更准 | ⏸ 按需开启 |

这个自由度在 `qwen3-vl-rerank` 降价后变得更有价值：**它现在的多模态价与文本价都是 0.5 元/百万 token**（2026-08-31 起，原多模态价 1.8），意味着开启多模态重排**不再有溢价**。所以这不是"省钱所以不做"，而是"**默认不必要，需要时零溢价可开**"——把选择权留给评测数据，而不是留给框架。

### 18.5 与"图文混合查询"的边界

需要明确区分三种查询形态，它们的实现难度差异很大：

| 查询形态 | 输入 | 实现 | 自研支持 |
|---------|------|------|---------|
| **以文搜图** | 文本 → 图片 | Caption 文本路召回 + 同一多模态模型编码查询文本与图片的视觉路召回 | ✅ 多模态一期 |
| **以图搜图** | 图片 → 图片 | 图片视觉向量 vs 图片视觉向量 | ✅ 一期可做，需前端支持粘贴/上传图片 |
| **图文混合查询** | 文本 + 图片 → 任意 | 多模态模型生成融合向量，或分别召回后做排名融合 | ⏳ 二期，需通过评测选择策略 |
| **以图搜文** | 图片 → 文本 | 只有当文本与图片由同一多模态模型编码时才可直接比较；否则先生成查询 Caption | ⚠️ 专项验证后开放 |

**建议的落地顺序**：**以文搜图 → 以图搜图 → 以图搜文 → 图文混合**。理由是以文搜图是绝对主流需求（用户想找图），且双描述方案在此效果最好；而"以图搜文"看似炫酷，实际命中率受限于跨模态语义鸿沟，容易做出来但不好用。

### 18.6 成本测算：图片嵌入不是障碍

以"**10,000 张图片，平均每张 1024×1024**"为假设（图片 token 按约 1000 估算，即 10 M 图片 token）：

| 方案 | 图片单价（元/百万 token） | 图片嵌入成本 | 备注 |
|------|----------------------|------------|------|
| `tongyi-embedding-vision-flash`（768 维） | 0.15 | **约 1.5 元** | ✅ 推荐，成本可忽略 |
| `tongyi-embedding-vision-plus`（1152 维） | 0.5 | 约 5 元 | 质量与成本平衡 |
| `qwen3-vl-embedding`（降维 1024） | 1.8 | 约 18 元 | 质量最优 |
| **Dify 内置图片嵌入** | 随 Dify 计费 | 未在本平台归集 | 口径不可控 |

**结论：图片嵌入本身便宜到可以忽略**——1 万张图最贵也就十几块钱。**真正的成本项是两处**：

1. **VLM 生成图片描述**（若开启 `caption-enabled`）：一张图约 200~500 输出 token，1 万张约 6~15 元（按 qwen-vl-max 级别价格）。**这笔钱买的是"图片可被文字搜到"的能力，性价比极高。**
2. **原图进 LLM 上下文**（默认关闭）：这才是真正会失控的一项，一张图 100~1000 token 且随 Top K 放大。**默认关闭就是这个成本控制策略本身。**

**所以图文 RAG 的成本结构，与第 10 章的结论完全一致：贵在 LLM 上下文，便宜在向量化。** 把原图挡在上下文之外，图文检索几乎是"免费"增加的。

### 18.7 与 Dify 的能力对比（结论）

| 维度 | Dify（v1.11+） | 自研 | 谁更优 |
|------|---------------|------|-------|
| 图文跨模态检索 | ✅ 支持 | ✅ 支持 | 持平 |
| 索引模式限制 | **仅高质量模式可用** | 经济模式亦可用描述文本做关键词检索 | **自研** |
| 重排模型要求 | **必须多模态，否则图片被剥离** | 无强制要求，纯文本重排不丢图 | **自研** |
| 向量空间治理 | 由 Dify 管理 | 文本与多模态空间显式隔离、分别评测 | **自研可控，但实现成本更高** |
| 图片检索的全文路召回 | ❌ 纯向量，关键词搜不到图 | ✅ 双描述使图片可被关键词命中 | **自研** |
| 原图进上下文 | 默认路径（成本高） | 默认关闭，按需开启 | **自研** |
| 图片访问安全 | 取决于部署 | 受控下载接口（修正 F12） | **自研** |
| 开箱即用程度 | ✅ 配置即用 | 需实现适配器与管线 | **Dify** |
| 生态与稳定性 | ✅ 成熟 | 需自建与维护 | **Dify** |

**结论**：Dify 适合快速交付现成图文检索，自研适合需要权限、成本、证据和索引策略可控的场景。是否迁移由同一数据集上的质量、延迟、成本和维护投入决定，不预设自研必然优于 Dify。

## 19. 附录

### 19.1 术语表

| 术语 | 含义 |
|------|------|
| 逻辑知识库 | 用户认知中的知识库实体，持久不变 |
| 索引版本 | 引擎+模型+参数的不可变组合，是切换的最小单位 |
| 能力槽位 | Parser / Chunker / Embedder / Retriever / Reranker 五个可替换位置 |
| 影子流量 | 主链路正常返回，影子链路异步记录以做对比 |
| 融合检索 | 向量召回与全文召回结果合并，常用 RRF 或加权 |
| 父子分块 | 子块用于召回匹配，父块用于提供生成上下文 |
| 语义缓存 | 按查询向量相似度复用检索结果，而非按字符串精确匹配 |
| 召回测试 | 绕过 LLM、直接观测检索结果的测试方式，用于验证库级检索配置 |
| 索引配置 | 影响向量生成的配置（索引模式、嵌入模型、分块），改动需重建索引 |
| 检索设置 | 仅影响查询时行为的配置（检索方式、TopK、阈值、重排），改动即时生效 |
| 分数构成 | 一条召回结果的向量分/关键词分/融合分/重排分，用于定位质量问题的环节 |
| 多模态嵌入 | 把文本与图片映射到同一语义空间的向量模型，支持跨模态检索 |
| 跨模态检索 | 用一种模态查询另一模态（以文搜图、以图搜文、以图搜图） |
| 统一语义空间 | 文本与图片向量处于同一坐标系，可直接比较相似度 |
| 向量空间 | 由模型、模型版本、维度和距离类型共同确定的可比较向量集合；维度相同不代表空间相同 |
| 图片降维 | 支持时通过模型的维度参数降低输出宽度；只解决存储约束，不改变空间隔离要求 |
| 双描述 | 同一张图片同时生成视觉向量和 VLM Caption；分别进入多模态空间与文本空间 |
| matchedBy | 图片被召回的方式：IMAGE_VECTOR（图片向量命中）或 TEXT_ONLY（跟随文本切片返回） |
| Vision 徽标 | 标识嵌入/重排模型具备图片理解能力，UI 上用于提示能力差异 |
