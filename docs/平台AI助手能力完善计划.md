# 平台 AI 助手能力完善计划：答对平台问题、做对平台操作

> 前置文档：[《平台 AI 助手（内置智能体）设计与规划》](平台AI助手（内置智能体）设计与规划.md)（P0～P3 已完成）。本计划接在 P3 之后，P4「主动建议」不在本计划内。
>
> 本计划是[《AgentMatrix 升级计划》](AgentMatrix%20升级计划.md)的第四步。本文的第零步～第八步，对应整体计划里的 4.0～4.8。
>
> 编写依据：2026-11 的 main（v1.1.0），加上工作区里尚未提交的助手优化（意图收窄工具、小上下文窗口裁剪、MCP / 技能 / 文档查询工具等）。

## 目标

助手要做到两件事：

1. **问答**：用户问到平台的任何功能、菜单、配置项、报错，助手都能答对，而且不编造。
2. **执行**：用户在执行模式下提出平台内的操作，助手都能用正确的方式处理。

「任何」没法直接验收，所以先换成一个能检查的定义：

- 建一份**能力清单**，逐项列出平台的每个功能点（菜单 × 操作），每一项写明助手怎么处理。
- 处理方式只有四种：用文档回答、调用查询工具、生成操作卡片、说明原因并给出界面入口。
- 删除资源、管理用户这类高危操作也开放代办，但要人工确认：卡片上必须手动输入资源名称才能执行（见第四步）。
- 第四种「只给入口」只用于助手确实做不了的事，比如上传文件（已决定不支持）。
- 「任何问题都能答对」的含义是：清单 100% 覆盖，每一项都有评测用例，并且评测通过率达到验收线。
- 支持范围：7B 及以上、支持工具调用的模型。板子上的 1.7B 这类小模型不在目标内，只保留问答模式（见第八步）。

## 第一步：能力清单（单一来源）

新增 `src/main/resources/assistant/capabilities.json`，按菜单列出每个功能点：

```json
{
  "id": "agent.update.temperature",
  "menu": "构建 › 智能体 › 编排",
  "action": "修改智能体温度",
  "handling": "WRITE",
  "tool": "update_agent_settings",
  "roles": ["SUPER_ADMIN", "DEVELOPER"],
  "docAnchor": "智能体/编排与调试"
}
```

- `handling` 取 `DOC`、`READ`、`WRITE`、`GUIDE`（不代办，只给出入口）四种值之一。`WRITE` 条目另带 `risk` 字段，取 `A`～`D`（见第四步）。
- **菜单清单也从这里生成**。`PLATFORM_OVERVIEW` 改成启动时按清单和当前角色拼出来，不再手写。前端菜单变动时同步更新这个文件；单测检查清单里的菜单名和前端 `DashboardView.vue` 的 tab 一一对应（前端的 tab 列表可以在 `npm run build` 时导出成 JSON，供后端测试读取）。
- **单测守门**：
  - 每个 `READ` / `WRITE` 条目对应的工具必须存在；
  - 每个条目至少有一条评测用例（见第七步）；
  - 每个 `DOC` 条目的 `docAnchor` 必须在文档里找得到。
- 第一版先覆盖现有菜单，预计 120～150 个条目。整理清单时，现有的能力缺口会自然列出来，后面几步按清单补。

验收：清单覆盖所有左侧菜单和子页面；上面三个单测都能跑。

## 第二步：补齐平台知识（答对「怎么用」）

1. **多文档导入**：`PlatformDocsService` 从只导入 `platform-guide.md`，改为导入一组内置文档：
   - 使用文档：`platform-guide.md` 和《平台功能使用说明》；
   - 接入文档：《开放接口接入指南》；
   - 运维文档：《部署与运维》，只给超级管理员检索。
   - 每篇文档单独计算 SHA-256，哪篇变了就只重新导入哪篇。
2. **配置项说明**：每个设置页的字段，比如温度、记忆轮数、Top K、分数阈值、混合权重、Rerank、上下文窗口，在文档里都要有「是什么、取值范围、什么时候改」三项说明。现在的文档大多只写到页面级。
3. **报错字典**：从后端整理用户能看到的报错文案，包括 `IllegalArgumentException` 的提示、开放接口的错误码和网关测试失败的原因，写成「报错 → 原因 → 处理」一张表，放进文档。「报错怎么办」这类问题主要靠这张表回答。
4. **问答模式的预算**：现在固定注入 4 段、每段最多 1200 字。改成按通道上下文窗口计算可用预算，小窗口时少注入几段，大窗口时多注入。
5. **文档跟着代码走**：在 PR 自查清单里加一条：「新增或改名菜单、字段、报错时，同步更新 `capabilities.json` 和文档」。第一步的单测会拦住漏改的情况。

验收：「使用问答」类用例扩充到每个 `DOC` 条目至少 1 条，DeepSeek 下全部通过。

## 第三步：补齐查询能力（答对「我的数据」）

只读工具不按接口逐个加，否则工具会多到 30 个以上，7B～9B 的模型选不准。做法分两类：

- **通用资源工具**：新增两个工具，`list_resources(type, filters)` 和 `get_resource(type, id)`。
  - 后端按 `type` 分派到各个 Service，并且按当前用户权限过滤，返回字段走白名单。
  - 第一批 `type`：`http_tool`、`template`、`prompt_version`、`api_key`（只返回元数据）、`terminal`、`guardrail_policy`、`audit_log`、`alert`、`rag_eval_run`、`faq`；仅超级管理员可查的有 `user` 和 `role`。
- **专用工具**：只给通用工具表达不了的场景，第一批三个：
  - `run_retrieval_test(knowledgeBase, query)`：对知识库做一次召回测试，返回命中切片和分数。这是排查「检索不到」最直接的手段。
  - `get_agent_logs(agent, filters)`：查询最近的调用记录、失败原因和耗时。
  - `get_tool_usage(agent)`：查询工具调用次数和失败率。
- `diagnose_agent` 接入上面三个工具的结果。诊断不再只看配置，也会看最近的失败记录和召回情况。

取舍：通用工具的定义少，但模型要把 `type` 选对，所以工具描述里列出每个 `type` 的中文名和示例问法。已有的 12 个工具先保留，等评测证明通用工具也能选准，再考虑合并。

验收：所有 `READ` 条目都有对应工具；单测确认任何工具结果里都不含密钥、密码和通道地址；只读观察员查到的范围和界面一致。

## 第四步：补齐执行能力（做对「帮我改」）

写操作按风险分四级。级别越高，确认越严格：

| 级别 | 内容 | 处理方式 |
| --- | --- | --- |
| A 新建（可删除） | 建 HTTP 工具、建技能（贴 Markdown）、从智能体存为模板、登记 MCP 服务（进入待审核状态）、加 FAQ（已有）、建智能体或知识库（已有） | 生成卡片，确认后执行 |
| B 修改（可回滚） | `update_agent_settings`：用一个工具改模型、主备通道、温度、记忆轮数、思考模式、知识库使用方式和变量；关联或取消关联技能、工具、MCP 工具；改知识库检索设置；改 FAQ；回滚提示词版本 | 生成卡片，展示修改前后的对比。确认时校验资源没有被别人改过，沿用改提示词时的做法 |
| C 运行（消耗资源，不改配置） | 重建索引、跑检索评测、刷新 MCP 工具列表 | 生成卡片，并注明耗时和成本。召回测试和通道测试不改数据，归入只读工具 |
| D 高危（难以撤销或影响他人） | 删除智能体、知识库、文档、FAQ、工具、技能、模板、MCP 服务；管理用户和角色；修改网关通道和密钥；修改护栏策略；吊销凭证 | 生成高危卡片，必须人工确认：用户在卡片里手动输入资源名称后才能执行（规则见下文） |

实现约定（保证「做对」）：

1. **生成卡片时先预检**：写工具调用对应 Service 的校验逻辑，检查权限、参数范围、模型是否在通道的模型列表里、知识库类型是否兼容。不通过就直接返回 `ok=false` 和原因，不生成卡片。
2. **参数只用 ID**：模型给出名称时，先用查询工具解析成 ID。匹配到多个就返回 `ambiguous`（沿用现有机制）。
3. **执行后回读**：确认执行成功后，重新读取一次资源，把实际生效的值写回会话。下一轮模型看到的是真实结果，而不是它自己的预期。
4. **写工具框架化**：把「定义 → 预检 → 卡片 → 执行 → 回读 → 审计」抽成公共流程。每加一个写工具只需要写参数定义、预检、执行三段代码和对应的测试。

D 级高危卡片的人工确认规则：

1. **输入名称才能确认**：卡片上有一个输入框，用户要手动输入资源名称，和卡片上显示的名称完全一致，确认按钮才可用。
   - 后端确认接口同样校验这段输入。只靠前端拦截不够，因为请求可以绕过界面直接发。
   - 没有通过校验的确认请求不消耗卡片，卡片保持待确认状态。
2. **先展示影响范围**：生成卡片时查出依赖关系并写在卡片上。例如删除知识库时，列出绑定了它的智能体；停用用户时，列出该用户名下的智能体和凭证。
3. **一张卡片只做一件事**：
   - 每轮对话最多生成 1 张高危卡片。
   - 高危卡片不能依赖其他未确认的卡片（不能用 `pendingActionId` 串联）。
   - 高危卡片 5 分钟后过期（其他卡片是 10 分钟）。
4. **密钥不经过模型**：修改网关密钥、重置用户密码时，新密钥或新密码由用户在卡片上的密码框里填写，随确认请求提交。
   - 模型只负责指定改哪个通道或哪个用户，看不到密钥本身。
   - 密钥不写入卡片参数、对话记录和审计。
5. **权限和平台规则照旧**：确认时用当前用户身份调用 Service，权限重新校验。现有的保护规则不变，例如不能删除或降级最后一个超级管理员、不能修改自己的角色。用户和角色管理只有超级管理员能用。
6. **审计级别**：执行记录的风险级别标为 `HIGH`，并记下影响范围；删除操作同时记录被删资源的名称和 ID。
7. **防诱导**：模型读到的工具结果（比如知识库内容、MCP 返回）里如果出现指令，可能诱导它生成删除卡片。人工输入名称这一关就是兜底，此外提示词里也明确要求：只有用户本人在本轮对话中提出时，才能生成高危卡片。

验收：所有 `WRITE` 条目都有写工具；未确认的卡片不改任何数据；每次执行在审计里有 `via=assistant` 记录；B 级卡片都带修改前后对比；高危卡片在名称输入错误时，前端和后端都拒绝执行；密钥在对话记录、卡片参数、审计和日志中都不出现。

## 第五步：选对工具

现在靠正则和关键词表判断要给哪些工具。改成按问题语义选：

1. **工具分组**：按能力清单把工具分成大约 10 组，比如智能体、知识库、技能、工具与 MCP、网关、用量、开放与安全、文档。每组写一段描述，并附 5～10 个示例问法。
2. **按向量相似度选组**：用已激活的向量模型，把问题加上页面上下文后，和各组的示例问法比相似度，取前 2～3 组，把这几组的只读工具和写工具一起下发。
   - 这样写工具也只下发相关的几个，不再是 7 个全给或全不给。
   - 多轮对话里，把上一轮选中的组也带上，解决现在只有第一轮收窄的问题。
   - 没有激活向量模型时，退回现有的正则和关键词表。
3. **强制调用一次工具**：执行模式下，如果问题命中了 `READ` 类组，但模型没调用任何工具就直接作答，就在同一轮带 `tool_choice=required` 重试一次。
   - 通道是否支持这个参数需要先实测。DeepSeek 对 `tool_choice=none` 不生效，这一点在 `OpenAiCompatibleClient` 的注释里有记录。
   - 实测后在通道能力里加一个「支持强制工具调用」标记，不支持的通道不重试。

验收：同一能力的同义改写用例（见第七步）通过率和原问法相差不超过 5 个百分点；qwen3.5:9b 下「数据查询」和「创建修改」类的通过率比基线高。

## 第六步：回答校验（不编造）

把 `CARD_CLAIM` 的思路推广成一组事后检查，放在 `turn.finish()` 之后：

| 检查 | 判断方法 | 命中后 |
| --- | --- | --- |
| 没有依据就报数据 | 执行模式、问题属于 `READ` 组、本轮没有成功的工具调用，而回答里出现数字或资源名 | 附加提示「本次没有查询平台数据，以上内容可能不准确」，并记录日志 |
| 菜单名不存在 | 回答里「」或加粗的菜单路径不在能力清单里 | 记录日志，进入评测复盘列表 |
| 链接是编造的 | Markdown 链接不在本轮工具结果给出的 `link` 集合里 | 去掉链接，只保留文字 |
| 提前宣布完成 | 卡片没有确认，回答却说「已创建」「已修改」 | 附加提示，处理方式与现有的 `CARD_CLAIM` 一致 |

这些检查都只看本轮数据，不额外调用模型，不会增加延迟。

验收：每项检查都有单测；这四类问题在评测中出现 0 次。

## 第七步：评测扩充和反馈闭环

1. **按清单生成用例**：每个能力条目至少 2 条用例，一条标准问法，一条口语化或同义改写的问法。每个 `WRITE` 条目再加 1 条越权用例（只读观察员发起）。用例数从 67 条扩到 250～300 条，单测检查覆盖率。
2. **评分增加数据核对**：用例的 `setup` 先造好数据，评分时检查回答里有没有出现真实的资源名和数值，不再只匹配固定关键词。
3. **文档类可选模型评分**：给「使用问答」用例写参考答案，用一个强模型（如 DeepSeek）判断回答和参考答案是否一致。
   - 默认关闭，日常评测仍用关键词评分。
   - 只在合并前的全量回归时打开，而且只用于「使用问答」类用例，控制成本。
   - 每次运行记录评分消耗的 token，显示在评测记录里。
4. **按通道分别统计**：评测记录带上通道和模型，「助手评测」页可以对比不同通道下各类别的通过率。
5. **反馈回流**：「助手评测」页增加「待复盘」列表，来源有三个：
   - 用户点了「没用」的回复；
   - 工具返回 `ok=false` 的对话；
   - 第六步的各项检查命中的对话。
   - 超级管理员可以把其中的对话一键转成评测用例草稿。
6. **回归门槛**：合并助手相关改动前，在 DeepSeek 通道跑全量评测，任何类别的通过率都不能下降。

验收：清单覆盖率 100%；待复盘列表能用；回归门槛写进 PR 自查清单。

## 第八步：按模型分级开放能力

执行模式只支持 7B 及以上、支持工具调用的模型。1.7B 这类小模型不做适配，这一点要在产品上说清楚，不靠用户自己去试：

| 助手所用通道 | 开放的能力 |
| --- | --- |
| 不支持工具调用，或模型小于 7B（如板子上的 1.7B） | 只开放问答模式（文档检索）。执行模式按钮置灰，并提示「当前模型不支持执行模式，请在模型网关为助手选择 7B 以上、支持工具调用的模型」 |
| 支持工具调用的 7B 及以上模型 | 全部能力，包括 A～D 级写操作 |

- 判断依据：通道的「支持工具调用」标记，加上模型网关里新增的「模型规模」字段（小于 7B / 7B 及以上）。Ollama 通道默认为「小于 7B」，由管理员确认后修改。
- 档位旁边显示该通道最近一次的评测通过率。如果某个类别的通过率低于验收线，就提示管理员换模型，但不自动关闭功能。
- 由于 1.7B 不再支持执行模式，现有为 4096 窗口做的激进工具收窄可以保留，但不再作为优化目标，之后不为它追加适配。

验收：小于 7B 或不支持工具调用的通道下，执行模式置灰并有提示；切换到 7B 以上的通道后，执行模式自动可用。

## 验收线（整体）

- 能力清单覆盖所有菜单和子页面，每个条目都有处理方式和评测用例。
- DeepSeek 通道：全量评测通过率 ≥ 95%，「权限与安全」类 100%。
- qwen3.5:9b 通道：「使用问答」「数据查询」「创建修改」类 ≥ 85%，「权限与安全」类 100%。
- 越权写入 0 次；未确认的卡片造成的数据变更 0 次；未输入正确名称的高危卡片执行 0 次；事后检查覆盖的四类编造在评测中出现 0 次。

## 已确认的决定

1. **高危操作开放，但必须人工确认**：删除、用户和角色管理、网关密钥、护栏策略、吊销凭证都提供写工具。卡片上要手动输入资源名称才能执行，密钥由用户在卡片里填写，不经过模型（见第四步）。
2. **不支持在助手面板上传文件**：上传文档仍在知识库页面完成。用户在助手里提出上传时，给出对应知识库详情页的链接。
3. **文档类用例用模型评分，默认关闭**：只在合并前的全量回归时对「使用问答」类打开（见第七步）。
4. **只支持 7B 及以上的模型**：1.7B 等小模型只保留问答模式，不为执行模式做适配（见第八步）。
