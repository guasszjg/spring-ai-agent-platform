# AgentMatrix 用户、角色与权限管理系统设计

版本：1.0（设计稿）  
日期：2026-09-08  
适用项目：`spring_ai` 后端、`spring_ai_ui` 前端  
交付范围：产品与技术设计文档，不包含业务代码、数据库变更或线上操作。

## 1. 建议采用的方案

采用 **固定角色 RBAC + 资源所有权 + 指定用户授权**。一期按“一个公司内部使用、一个平台实例”设计。

- 角色决定“能做什么”：例如开发者可以创建智能体，但不能管理模型供应商。
- 资源关系决定“能对谁的数据做”：开发者管理自己的智能体，也可以使用管理员明确授权的知识库。
- 系统状态决定“现在是否允许”：账号被禁用、API Key 被撤销或智能体已停用，都必须阻止调用。

一期提供三个固定角色：**超级管理员、开发者、只读观察员**。先由现有管理员创建开发者，逐步分配资源；观察员适合只查看运行情况的同事，可暂不创建此类账号。角色管理页面先展示权限和维护角色成员，不开放任意修改权限。自定义角色、部门、项目空间与 SSO 放到后续阶段。

这样可以先把当前最重要的管理员与开发者边界做完整，同时避免一期就引入复杂的组织与审批系统。

### 1.1 贯穿全篇的例子

管理员创建开发者“小王”和“小李”，配置平台可用模型。小王创建“客服助手”和“售后知识库”，默认只有小王和管理员能管理。小王将知识库以“可使用”授权给小李后，小李可以挂载到自己的智能体，但不能浏览原始文档或修改 FAQ。管理员可以将小王的智能体以“可查看”授权给观察员，观察员只能看名称、状态和聚合指标，看不到提示词、客户对话和密钥。

小王离职时，管理员先禁用其账号，使其 Session 和个人签发的 API Key 失效，再将资源移交给小李。业务接入方使用小李重新签发的 Key 恢复调用。资源移交不会自动把原有访问授权扩大。

## 2. 现状与设计依据

以下结论来自本地代码，未访问数据库确认账号记录。用户反馈“目前只有管理员可用”作为实际部署现状。

| 当前实现 | 对本设计的影响 |
| --- | --- |
| `AppUser` 已有 id、username、password、nickname、role、avatar、uiPreferences | 扩展现有用户表，无需重做用户模型 |
| `DataInitializer.seedUsers()` 在空用户表且演示开关开启时创建 admin/developer；非空表不会补建缺失 developer | 演示账号入口不等于真实用户管理；账号创建必须改为明确的管理流程 |
| 初始化逻辑会将已有演示用户密码恢复为固定值 | 上线用户管理前必须移除此重置行为，避免修改密码后重启又被覆盖 |
| `SessionAuthInterceptor` 只检查 Session 内是否存在用户 | 当前 role 主要用于显示，缺少角色授权、用户状态校验和资源权限 |
| `AuthController.me()` 在查不到用户时可回退到旧 Session 数据 | 新设计必须拒绝不存在或已禁用的用户，禁止旧 Session 继续生效 |
| Agent、知识库、模板没有统一资源所有者；日志主要按 agentId 查询 | 需要补充归属字段和按权限过滤的查询 |
| 管理端接口直接接收或返回部分 JPA 实体 | 需要 DTO 白名单，防止客户端修改 owner、role、apiKey 等字段 |
| Agent API Key 存在 `agents.apiKey`，开放 API 以它鉴权 | 人员 Session 与机器凭据应分开管理 |
| Bocha 密钥能回退到其他任意 Agent 保存的密钥；复制 Agent 会复制密钥 | 必须改成显式平台凭据与资源专属凭据，禁止跨所有者隐式借用 |
| 网关有主备路由和 Spring AI 默认调用路径 | 每一条执行路径都需要权限校验，不能借助回退绕过授权 |
| FAQ 图片通过 `/uploads/**` 直接访问 | 私有知识库的附件也要受访问控制，不能只保护列表接口 |

## 3. 范围与默认规则

### 一期必须完成

用户创建、编辑、禁用、恢复、密码重置、首次改密；固定角色与成员维护；资源所有权与显式共享；权限即时撤销；菜单和按钮控制；Session 与 API Key 分开鉴权；用户与授权操作审计；历史数据迁移。

### 后续扩展

自定义角色、多角色叠加、部门树、项目空间、多租户、SSO、MFA、邀请邮件、业务审批、企业服务账号、自动化离职同步。它们不是一期验收前置条件。

### 一期统一约定

1. 不开放自助注册；由管理员创建账号。
2. 每个用户只有一个角色，角色编码稳定，显示名可以本地化。
3. 新资源默认私有；不设置“所有开发者自动可见”的隐式规则。
4. 超级管理员管理全平台业务资源，但也不能读取保存后的密钥明文。
5. 开发者可以向指定的有效用户共享自己资源的有限能力，不能授予编辑、密钥管理、转移或再次共享权限。
6. 共享授权与角色能力取交集。给观察员授权“可使用知识库”，也不会使其获得模型调用能力。
7. 用户禁用不删除资源；普通管理页面不提供物理删除用户。
8. 普通请求只允许访问状态为 ACTIVE 的资源所有者所拥有的资源；管理员可以查看、移交被禁用用户的资源，但也不能继续执行其智能体。

## 4. 角色权限矩阵

“自己”均指 owner_user_id 等于当前用户；“授权”指存在有效资源授权记录。角色名字不写进页面和业务判断，使用权限编码。

| 功能 | 超级管理员 SUPER_ADMIN | 开发者 DEVELOPER | 只读观察员 VIEWER |
| --- | --- | --- | --- |
| 修改本人资料、密码、退出登录 | 允许 | 允许 | 允许 |
| 创建账号、禁用账号、重置他人密码 | 全平台 | 禁止 | 禁止 |
| 分配角色、查看角色成员 | 全平台 | 禁止 | 禁止 |
| 查看业务概览 | 全平台 | 自己及授权资源的聚合数据 | 明确授权资源的聚合数据 |
| 创建智能体 | 允许 | 允许 | 禁止 |
| 查看智能体名称、状态、聚合指标 | 全平台 | 自己或授权 | 授权 |
| 查看完整提示词、配置 | 全平台 | 仅自己 | 禁止 |
| 编辑、复制、删除、启停智能体 | 全平台 | 仅自己 | 禁止 |
| 调试并调用智能体 | 全平台有效资源 | 自己或被授予 RUN | 禁止 |
| 查看智能体完整会话正文 | 全平台，访问留审计 | 仅自己资源，访问留审计 | 禁止 |

| 签发、撤销 Agent API Key | 全平台 | 仅自己 | 禁止 |
| 创建和管理知识库、文档、FAQ | 全平台 | 仅自己 | 禁止 |
| 挂载知识库进行检索 | 全平台有效资源 | 自己或被授予 USE | 禁止 |
| 浏览知识库原文和附件 | 全平台 | 仅自己 | 禁止 |
| 查看知识库名称等非敏感元数据 | 全平台 | 自己或授权 | 授权 |
| 从 Dify 全量同步知识库 | 允许 | 禁止 | 禁止 |
| 创建、编辑、删除个人模板 | 允许 | 仅自己 | 禁止 |
| 使用模板创建智能体 | 允许 | 自己、平台模板或被授予 USE | 禁止 |
| 发布、更新平台公共模板 | 允许 | 禁止 | 禁止 |
| 使用已开放的模型和平台工具 | 允许 | 允许，受启用状态与额度约束 | 禁止 |
| 管理供应商、模型路由、平台密钥 | 允许 | 禁止 | 禁止 |

观察员一期不读取业务正文，目的是避免“只读”被误解为可以查看所有敏感数据。后续有运营人员查看对话的需求，再新增独立的 `conversation:read` 授权能力和专门角色。

## 5. 资源权限与共享

### 5.1 资源分类

| 分类 | 包含内容 | 权限来源 |
| --- | --- | --- |
| 私有业务资源 | Agent、知识库、个人模板 | 所有者 + 指定用户授权 |
| 子资源 | 知识文档、FAQ、图片、Agent 工具凭据 | 继承父资源，不单独共享 |
| 会话资源 | 对话会话、消息、流任务 | 父 Agent 管理权限，或会话发起者身份 |
| 平台资源 | 模型供应商、路由策略、平台工具凭据、内置模板 | 固定角色权限与平台开放策略 |
| 系统资源 | 用户、角色、授权记录、审计日志 | 管理员权限；个人资料例外 |

### 5.2 一期共享级别

| 资源 | 可授予级别 | 明确允许 | 明确不允许 |
| --- | --- | --- | --- |
| Agent | VIEW | 名称、描述、状态、聚合指标 | Prompt、完整配置、历史对话、密钥、调用 |
| Agent | RUN（包含 VIEW） | 调用已保存配置，查看自己的调用会话 | 改 Prompt、改工具、改模型、挂载新知识库、读取他人会话 |
| 知识库 | VIEW | 名称、描述、索引状态、文档数量 | 原始文档内容、FAQ 答案、附件下载 |
| 知识库 | USE（包含 VIEW） | 在自己 Agent 中绑定并通过 RAG 检索 | 原文列表、下载、增删改文档、转授权 |
| 个人模板 | USE | 阅读模板内容并复制为自己的 Agent | 修改源模板、删除源模板、共享源模板 |

“可使用知识库”意味着允许其内容以检索片段和模型回答的形式被使用，不能承诺内容永不被提取。共享弹窗必须说明：接收方可以让自己的 Agent 使用这些知识，并可将回答能力提供给其应用用户。需要禁止这种传播的数据，一期应保持私有。

平台模板视为管理员向所有有效开发者发布的 USE 授权；观察员不读取其 Prompt。管理员若希望开发者共同编辑同一个 Agent，可先转移所有权；协作者编辑角色留到二期。

### 5.3 授权判定

```text
允许 = 主体有效
    且具有操作权限
    且资源关系允许
    且依赖资源授权有效
    且资源和凭据状态允许
```

判断顺序：认证 → 用户状态/权限版本 → 操作权限 → 所有者或共享关系 → 父子资源归属 → 依赖授权 → 执行。未知权限、未知资源类型与缺失 owner 均默认拒绝。

示例：小李读取小王 Agent 的日志，即使知道 Agent ID 且获得 RUN，也不具有 `agent:logs:read` 对该资源的关系授权；只能读取自己发起的会话。

### 5.4 特殊操作

- **复制 Agent**：一期限所有者与管理员。创建新 ID、新 owner；清空专属凭据、API Key、会话、统计与共享关系；只保留新 owner 有权使用的模型和知识库绑定。缺少依赖时保存为 IDLE 并提示重新配置。管理员复制他人资源默认归管理员自己。
- **共享撤销**：下一次请求生效；不抹除已经合法交付的回答。撤销知识库 USE 后，引用该库的 Agent 标记依赖失效，下一次调用在请求模型前失败，禁止静默忽略该库继续回答。
- **授权缩减或资源转移**：重新检查所有依赖授权，不凭“以前绑定成功”放行；已有共享记录默认保留，但转移页面展示供管理员明确撤销。
- **父子资源**：使用 `/knowledge-bases/{kbId}/documents/{docId}` 必须同时验证 doc 属于 kb；FAQ、图片、日志、流任务同理。
- **列表与统计**：在 SQL 查询中先限定资源范围，再分页、计数与聚合；不先返回全平台数据给前端隐藏。
- **共享用户选择**：开发者仅查询有效 DEVELOPER/VIEWER 的 id、用户名、昵称，要求关键词、限制分页并限流；不能借此读取用户状态管理、邮箱或其他系统信息。

## 6. 用户生命周期与管理流程

### 6.1 用户字段与状态

角色：SUPER_ADMIN / DEVELOPER / VIEWER。状态：PENDING_PASSWORD / ACTIVE / DISABLED。短期登录锁定使用独立 `locked_until` 字段，不与管理员禁用混淆。

| 操作 | 结果 |
| --- | --- |
| 管理员创建用户 | 状态 PENDING_PASSWORD，生成一次性临时密码，首次登录强制修改 |
| 临时密码登录 | 仅允许访问本人状态、CSRF Token、修改密码、退出；禁止所有业务请求 |
| 完成首次改密 | 进入 ACTIVE，更换 Session ID |
| 管理员重置密码 | 进入 PENDING_PASSWORD，旧 Session/个人 API Key 失效，新临时密码一次展示 |
| 用户主动修改密码 | 校验原密码，其他 Session 和本人签发 Key 失效，当前会话重新建立；页面事先提示影响 |
| 管理员禁用 | 进入 DISABLED，下一次请求拒绝，资源保留，调用入口停止 |
| 管理员恢复 | 进入 PENDING_PASSWORD，要求重新设置密码；旧 API Key 不恢复 |
| 用户角色变更 | 下一次请求按新角色计算；旧 Session 失效；该用户签发 Key 撤销 |

临时密码建议有效期 24 小时，只存密码哈希。过期后由管理员重新生成；不通过日志或普通用户详情显示。不提供固定默认密码。

### 6.2 管理员保护

- 不允许禁用自己或将自己从 SUPER_ADMIN 降级；由另一管理员操作。
- 不允许禁用、降级最后一名 ACTIVE 的超级管理员。
- 上述规则需在事务内串行保护管理员集合，避免两个并发操作各自通过检查后使管理员数量变为零。
- 创建超级管理员、修改角色、重置他人密码、转移资源要求管理员重新确认本人密码；服务器验证近期重认证状态，建议有效 5 分钟。
- 用户名按不区分大小写唯一存储，创建后不可修改；昵称可修改。
- 角色分配、状态修改、密码重置使用专门接口，不接受通用用户更新请求顺带修改这些字段。

### 6.3 离职交接

1. 管理员禁用用户，立即阻断新的请求与个人 Key 调用。
2. 查看该用户资源、共享关系、相关 API Key，以及引用其知识库的其他 Agent。
3. 选择有效 DEVELOPER 或 SUPER_ADMIN 接收资源，检查其模型与知识库使用权限。
4. 转移所有权，保留原创建人和审计记录；按 Agent/知识库依赖成组交接，不能一半成功却提示全部完成。
5. 撤销这些资源现存 Key，接收人重新签发并更新应用配置；专属工具凭据标记待替换，重新配置后才能调用。
6. 管理员确认共享列表和失效依赖，保留禁用用户作为历史记录。

一期接受“禁用或交接期间关联服务暂停”的明确行为。如后续要求员工离职不影响生产服务，应增加企业服务账号作为资源所有者和机器凭据主体。

## 7. 登录、Session 与权限撤销

管理端继续使用同源 Session，建议通过 Spring Security 接管认证和方法授权，不为了角色管理改成 JWT。现有密码哈希可兼容沿用。

- Session 只保存稳定 userId、authVersion、登录时间等身份数据；不将角色显示字符串作为可信授权依据。
- 每个受保护请求读取用户当前状态和 authVersion；不一致则清除会话并返回 401。角色能力使用后端固定映射；一期优先正确性，不引入长期权限缓存。
- 资源授权每次从数据库判定；管理员撤销共享后，下一次请求立即生效。
- 使用 CSRF Token 保护 Session 登录和所有修改操作。提供匿名 CSRF 初始化端点，前端通过请求头提交；登录后刷新 Token。
- `/api/v1/**` 使用独立 Bearer/API Key 认证，不回退使用 Cookie，只有这组无 Cookie 身份的端点可豁免 CSRF。
- `/api/auth/me` 返回 userId、username、nickname、roleCode、roleName、permissions、状态和偏好，不返回密码、密钥和内部连接配置。
- 登录失败返回统一文案。建议初始限流：每用户名 15 分钟内连续 5 次失败触发 15 分钟临时锁定，同时按 IP 限速；阈值配置化，不采用可被攻击者永久锁死的规则。
- 保留现有 HttpOnly、SameSite 和生产 Secure Cookie。登录、重认证与密码修改不记录请求正文。

“立即撤销”的边界是下一次授权检查：已发送至外部模型的请求不能保证撤回。SSE 注册主体与任务关系，发送后续分片前检查撤销状态，终止输出并尽力取消上游；已产生用量保留记录。写入操作在事务提交前复核敏感状态，防止禁用与写操作竞争。

## 8. 模型、工具、RAG 与开放 API 的边界

### 8.1 模型网关

一期由管理员配置模型并选择是否“向开发者开放”。开发者只看到模型标识、显示名、能力和可用状态，不能看到 Base URL、自定义 HTTP 头、请求体模板或供应商 Key。

开发者选择模型需通过 `model:use` 和开放状态检查；执行时重新检查。主路由、备用路由与默认 Spring AI 路径都只能使用授权模型；主模型故障不得切换到未授权供应商。建议一期将默认调用路径也注册为平台模型，统一路由。

由管理员初始设置开发者每日请求上限和并发上限，具体额度按容量配置；失败返回 429。Token 成本用于观测，不以自定义 HTTP 返回的估算 Token 做精确账务结算。按开发者、Agent 和 Key 三种维度记录消耗。

### 8.2 工具凭据

凭据解析顺序限定为：该 Agent 专属凭据 → 管理员明确开放的平台凭据 → 未配置。

禁止搜索其他 Agent 的凭据。普通接口只返回 configured、source、updatedAt，不返回保存后的明文或密文。复制不继承专属凭据，转移后需要替换。

工具调用前计算“角色可用工具 ∩ Agent 已启用工具 ∩ 平台允许工具”。RUN 用户及 API 调用者不能用请求体临时打开工具或注入 Key；所有者调试如需临时 Key，仅允许在其自有 Agent 的专门调试 DTO 提交，不持久化、不回传、不进入模型上下文。

### 8.3 知识库依赖

保存 Agent 的知识库绑定时，检查所有者对每个知识库具有 USE；每次执行再次检查。

对于共享 RUN 和开放 API，由 Agent 所有者作为依赖授权主体，调用人不需要另外获得知识库 USE。这是一种明确的能力委托：授权 RUN 就允许获得此 Agent 基于其合法知识库生成的回答；不能据此访问原始知识库接口。

开发者只能创建新的 Dify 数据集映射，不能提交任意 externalDatasetId 占用平台已有数据。Dify 全量同步仅管理员可用，导入的数据初始归管理员、默认私有。Dify 连接 Key 具有较大上游访问范围，本地权限必须在调用 Dify 前检查。

FAQ 图片改为受控附件：数据库记录所属知识库/FAQ，下载通过鉴权接口读取，不直接公开物理路径。先上传再关联的图片使用临时附件记录，仅上传者可访问，关联时验证所有者，过期清理未关联文件。历史路径迁移后关闭 `/uploads/**` 的匿名访问。

### 8.4 API Key

引入独立的 `agent_api_keys`，支持一个 Agent 多个接入 Key。Key 只授予 `chat:invoke` 和操作本人流任务的 `chat:stop`，不具备用户或资源管理能力。

- 服务端生成高随机 Key；明文只在创建时展示，存储不可逆哈希及可展示前缀。
- 记录 keyId、agentId、createdBy、issuerAuthVersion、过期时间、撤销时间、最近使用时间、额度。
- 每次调用检查：哈希正确、未过期/撤销、签发人 ACTIVE 且版本匹配并仍有该 Agent 签发资格、资源 owner ACTIVE、Agent RUNNING、依赖有效、额度允许。
- 禁用签发人或改变其角色使其 Key 失效；Agent 转移撤销该 Agent 全部 Key；超级管理员签发的 Key 也遵循状态规则。
- 管理端 Session 请求不能因“有 Agent 页面权限”自动通过开放 API；页面调试使用管理端接口，API 测试组件显式传新 Key。
- 开放 API 接收 message、conversation_id、response_mode、user 等业务字段；不允许客户端指定 owner、模型、Prompt、任意知识库和工具凭据。
- `user` 是可信后端应用填写的外部用户标签，不是平台身份认证。会话限定为 `(agentId, keyId, externalUser)`，不能仅凭 conversationId 续接。
- 同一 Key 持有人可以伪造任意 user，故 Key 仅部署在可信服务端；不嵌入浏览器。终端用户隔离由接入应用先完成认证。本平台不能将自行提交的 user 当成安全证明。
- Session 调试会话按 `(agentId, userId)` 隔离；用户输入的 account 仅可作显示标签，真实 actor 来自认证上下文。
- stop 接口校验 taskId 对应同一 Key/会话主体并实际取消；取消功能未实现前返回明确“不支持”，不虚报成功。

## 9. 页面与交互设计

### 9.1 导航

现有侧栏保留概览、智能体、模板、知识库。管理员可见模型网关，新增“用户管理”“角色权限”“操作审计”。所有人可进入“个人设置”。权限数据来自 `/api/auth/me`，资源行内操作来自后端返回的 `allowedActions`。

登录页删除固定账号/密码自动填充。若需要演示，应单独启用演示环境并明确标注，生产页面不显示快捷账号。侧栏显示真实昵称和角色，不再固定写“租户主账号”。

### 9.2 用户管理

列表列：用户名、昵称、角色、状态、最近登录、创建时间、操作。支持关键词、角色、状态筛选与数据库分页。

创建弹窗：用户名、昵称、角色（默认开发者），提交后一次展示临时密码和有效期。关闭前提示管理员安全交付给本人。详情抽屉包括基本信息、资源数量、已签发 Key 数量和近期账号操作。

行操作：编辑昵称、修改角色、重置密码、禁用/恢复、资源交接。禁用前展示受影响资源与 Key 数量；角色变更前展示将失去的能力，尤其是 API 服务可能停止。只读观察员拥有历史资源时，降级后保留归属，但管理员必须负责后续转移，原用户不能管理或执行。

### 9.3 角色权限

一期展示三个内置角色卡片，点开查看按模块组织的权限矩阵和成员列表。内置权限不可编辑；管理员可从成员页为用户选择角色。权限旁说明数据范围，例如“编辑智能体：本人资源”，不能只写模糊的“智能体管理”。

二期提供“复制开发者角色”创建自定义角色，后端仅接受已注册的权限编码；超级管理员是不可复制或编辑的保护角色。

### 9.4 资源列表与共享

开发者列表增加“我的 / 授权给我”；管理员增加所有者筛选。共享资源显示来源用户和 VIEW/RUN/USE 标记。资源详情的“共享”弹窗包含接收人、级别、已有授权与撤销操作。

共享知识库时显示内容传播说明；共享 RUN 时显示“对方可通过此 Agent 获得知识库回答，但不能查看配置”。没有权限的按钮隐藏；资源尚未满足执行条件时保留按钮并禁用，说明“知识库授权已撤销”等可行动原因。

RUN 用户进入受限对话页，仅显示输入与自己的会话；不要复用完整 DebugView 后仅隐藏左侧，因为仍可能加载配置和日志。

### 9.5 错误体验

- 401：会话失效，跳转登录；未保存编辑可暂存在内存，不能缓存密钥。
- 403：操作不允许，显示缺少的能力说明，不泄露资源详情。
- 404：对不可见的资源 ID 与真实不存在 ID 统一处理。
- 409：资源依赖失效、版本冲突、最后管理员保护等，显示明确业务错误码。
- 429：超过限流，显示可重试时间。

前端隐藏按钮改善体验，后端校验才是最终边界。处理直达 URL、页面打开后被撤权和提交期间角色改变等情况。

## 10. 数据模型

以下是建议字段与约束，不是可直接执行的数据库迁移脚本。统一沿用现有字符串 ID；时间建议明确 UTC 存储、显示时转换时区。

| 表/实体 | 新增或关键字段 | 约束与用途 |
| --- | --- | --- |
| app_users | role_code、status、auth_version、must_change_password、temp_password_expires_at、locked_until、failed_login_count、last_login_at、created_by、created_at、updated_at、version | role_code 外键；用户名规范化唯一；auth_version 用于撤销身份；原 password 字段保留哈希 |
| auth_roles | code、name、description、builtin | 一期仅三条内置记录，code 主键 |
| auth_permissions | code、module、name、description | 由版本迁移注册权限，不接受前端随意新增 |
| auth_role_permissions | role_code、permission_code | 联合唯一；一期固定种子数据 |
| agents / knowledge_bases / agent_templates | owner_user_id、created_by、updated_by、version | owner 外键非空；禁止由普通更新 DTO 修改；平台模板通过 builtin 标记区分 |
| resource_grants | resource_type、resource_id、grantee_user_id、level、granted_by、created_at | `(resource_type, resource_id, grantee_user_id)` 唯一；level 按资源类型限制 |
| agent_api_keys | id、agent_id、key_prefix、key_hash、created_by、issuer_auth_version、scopes、expires_at、revoked_at、last_used_at、request_limit | key_hash 唯一；不存明文；外键指向 Agent 与用户 |
| agent_conversations | actor_type、actor_user_id、api_key_id、external_user_id | USER 与 API_KEY 两种模式互斥；历史未识别身份只允许 owner/admin 查看 |
| knowledge_attachments | id、knowledge_base_id、faq_id、uploaded_by、storage_key、mime_type、size、status、expires_at | 临时上传与正式附件分开，下载校验父资源 |
| platform_tool_credentials | tool_code、encrypted_secret、enabled_for_developers、updated_by、updated_at | 替代跨 Agent 随机取密钥；密文仅内部读取 |
| audit_events | id、occurred_at、actor_type、actor_user_id、api_key_id、action、resource_type、resource_id、result、reason_code、request_id、client_ip、sanitized_diff | 追加写入；业务端无修改/删除接口；敏感字段脱敏 |

一期一个用户一个角色，暂不需要 user_roles 表。多角色时再增加关联表并定义冲突规则。`resource_grants` 的多态 resource_id 无法通过普通单列外键关联三个表，必须用资源专用 Service 验证存在性、事务内删除相关授权，并做孤儿记录检查；若团队优先数据库强约束，也可拆成三张同构授权表。

建议索引：资源 `(owner_user_id, updated_at)`；授权 `(grantee_user_id, resource_type, resource_id)`；会话 `(agent_id, actor_user_id, updated_at)` 与 `(agent_id, api_key_id, external_user_id)`；审计 `(occurred_at)`、`(actor_user_id, occurred_at)`、`(resource_type, resource_id, occurred_at)`。

删除资源时清理子资源、授权和凭据；审计保留资源标识快照，不做级联删除。用户停用不级联删除任何业务数据。

### 11.2 权限编码

固定格式 `领域:动作`，必要时三级。核心编码：

```text
user:read  user:create  user:update  user:assign-role
user:change-status  user:reset-password  user:transfer-resources
role:read  audit:read
agent:create  agent:view  agent:config:read  agent:update
agent:delete  agent:copy  agent:status:update  agent:run
agent:logs:read  agent:metrics:read  agent:key:manage
knowledge:create  knowledge:view  knowledge:content:read
knowledge:update  knowledge:delete  knowledge:use  knowledge:sync
template:create  template:view  template:use  template:update
template:delete  template:publish
model:use  gateway:manage  tool:use  tool:credential:manage
resource:share
```

permission 只是动作许可，`agent:update` 并不代表可以编辑任意 Agent。创建、详情、搜索、附件、批量操作、后台任务都必须使用同一套资源策略。

## 12. 审计设计

至少记录：登录成功/失败、用户创建、角色变更、禁用恢复、密码重置、授权授予撤销、资源转移、Key 签发撤销、平台凭据替换、网关修改、资源删除、完整对话正文访问、重要越权拒绝。

成功的权限/身份变更与审计事件在同一数据库事务提交；审计写入失败则回滚该敏感变更。鉴权失败事件用独立事务记录，防止业务回滚带走失败证据；失败风暴按账号/IP聚合限流，保留计数。

记录“管理员 A 将用户 B 从 DEVELOPER 改为 VIEWER”，不记录密码、Authorization、API Key、密文、完整 Prompt 或客户对话。自定义 HTTP 配置只记录修改了哪些字段，不能把 headers/body 原样放入 diff。反向代理 IP 仅信任部署配置中的代理来源。

建议初始审计保留 180 天，期限由实际运营要求决定；归档清理由独立维护流程执行，业务用户无修改/删除入口。下载审计报告可留二期。

## 13. 历史数据迁移与上线顺序

1. **盘点与备份**：备份数据库，确认真实管理员 ID、全部用户角色值、资源数量、Key 数量和未归属记录。不要仅凭 username=admin 自动授予超管；由部署配置指定经确认的 bootstrapAdminId。
2. **移除演示重置**：生产关闭演示账号，删除启动时恢复固定密码的逻辑；不因新增权限功能自动创建一个公共 developer 账号。
3. **扩展表结构**：通过版本化迁移新增角色、权限、状态、owner、共享、Key、附件和审计结构；先允许待回填 owner 为空。
4. **映射人员**：确认的现有管理员映射 SUPER_ADMIN；其余账号逐条核对。未知角色/演示账号先设 DISABLED，不自动赋予开发者或管理员。保留现有密码哈希，首次进入新系统要求改密。
5. **回填资源**：历史 Agent、知识库、模板归经确认的管理员。平台内置模板标记为 builtin。历史会话保留原 account 作显示标签，真实 actor 未知，不通过同名字符串绑定平台用户。
6. **迁移凭据**：现有 Agent Key 哈希迁入新表，签发主体指定确认的迁移管理员，并标注 migrated；从此普通详情不回传 Key。迁移时给旧 Key 设置明确失效日期，建议切换后 7 天，管理员提前向接入方交付新 Key。已有泄露风险的 Key 直接撤销，不套用宽限期。
7. **迁移工具与附件**：按实际归属保留 Agent 专属密钥；共享平台 Key 由管理员显式选择配置，禁止继续任意回退。建立附件归属，无法确认归属的附件隔离至管理员可见；更新内容链接并关闭匿名路径。
8. **加强约束与启用权限**：核对行数、owner、角色、依赖后添加 NOT NULL/FK/索引；执行完整验收。正式切换时停止旧版本写入，清除旧 Session，启用新 API 身份流程。
9. **小范围试用**：先创建两个开发者与一个观察员，完成共享、撤权、交接与 API 调用验收，再开放更多账号。

Key 哈希化后不可从数据库恢复明文，不保留可逆副本。不要在旧版本仍运行时清除其必需字段；切换窗口统一升级，随后清理明文旧列。回滚优先停服修复或回滚到兼容新鉴权的数据版本，禁止简单恢复无授权旧代码对外服务。数据库备份含敏感信息，应限制访问并按计划销毁。

## 14. 开发阶段与验收边界

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| A：身份底座 | 用户生命周期、固定角色、Session 版本、CSRF、用户与角色页面 | 能创建开发者；改密/禁用/角色改变即时失效；不能越权管理账号 |
| B：资源边界 | owner、查询隔离、共享、模型/工具/RAG 依赖、附件授权 | 两个开发者互不越权，共享级别严格生效，撤销不被回退绕过 |
| C：机器凭据与审计 | Key 表、会话/任务隔离、限流、敏感事件审计 | Key 不能访问管理 API，撤销与离职正确阻断，操作可追溯 |
| D：迁移与交接 | 历史回填、旧 Key 切换、资源转移、回归测试 | 数据保留、管理员不丢失、旧权限路径全部关闭 |

阶段 A 完成后不应单独宣称“多用户权限已上线”；A–D 全部完成才满足一期交付。后续再按真实需求引入业务管理员、自定义角色和项目空间，不必先拆微服务。

## 15. 核心验收用例

测试数据：管理员 A、开发者 B/C、观察员 D；B/C 各有 Agent、知识库、模板和 Key。接口集成测试必须使用独立测试数据库与模拟外部模型/Dify，不访问真实公网服务。

| 场景 | 预期 |
| --- | --- |
| B 调用用户创建、网关编辑接口 | 403，数据库不变 |
| B 直接猜 C 的 Agent/知识库/附件 ID | 404，无详情泄露 |
| B 修改请求中的 owner、role、统计、apiKey | DTO 拒绝或不接受字段，授权主体不变 |
| B 创建 Agent 时绑定 C 的私有知识库 | 拒绝，在调用 Dify 前失败 |
| B 将知识库 USE 授予 C | C 可挂载和检索，不能下载原始文档或修改 FAQ |
| B 撤销 C 的 USE，C 调用已绑定的 Agent | 依赖失效，模型与 Dify 均未调用 |
| D 获得 Agent VIEW | 可看元数据与聚合指标，不能调试、读取 Prompt/日志 |
| C 获得 B 的 Agent RUN | 可调用已存配置；不能改工具/模型；只能查看自己的会话 |
| 主模型故障，备用模型未开放 | 拒绝备用路径，不绕过模型授权 |
| B 的 Agent 未配置 Bocha Key，C 已配置专属 Key | B 不能借用 C 的 Key，只能使用显式平台凭据 |
| A 禁用 B，B 已登录且持有 Key | 下一次 Session/API 请求拒绝，B 拥有的 Agent 不执行 |
| B 被降为观察员 | 会话失效、签发 Key 失效，不能继续管理历史资源 |
| 两个管理员并发禁用/降级对方 | 事务保护保证至少一个 ACTIVE 超管 |
| Key 调用 /api/users 或修改 Agent | 拒绝，不能借用同请求 Cookie 放行 |
| Key1 使用 Key2 的 conversationId/taskId | 拒绝，不续接、不停止他人任务 |
| 客户端伪造 account/owner | 审计和会话身份仍取认证上下文 |
| 一次性临时密码过期或未改密访问业务 | 拒绝；只允许改密流程 |
| 跨站 Session 写请求没有 CSRF Token | 拒绝 |
| 分享/转移后旧页面提交更新 | 重新授权与版本检查，不覆盖新 owner 数据 |
| 复制/转移 Agent | 密钥不复制，Key 按规则撤销，依赖重新校验 |
| 读取页面源、用户详情、Agent 列表、审计 diff | 不含密码或保存后的 Key/密文/供应商凭据 |
| B 查看概览、数量、排行榜 | 只聚合允许范围，未授权资源不影响显示总数 |
| 迁移旧会话身份无法识别 | 仅资源 owner/admin 可读取，不误认同名用户 |
| 敏感权限变更时审计写失败 | 变更回滚，不产生无审计授权 |

权限验收重点是“后端拒绝且没有外部调用或写入副作用”，不能只检查按钮是否隐藏。测试需覆盖管理端直连接口、开放 API、内部调用与所有回退路径。

## 16. 一期决策清单

本稿采用以下默认产品决策，可直接作为后续开发基线：单平台；管理员创建用户；三种固定角色；一个用户一个角色；资源默认私有；开发者仅编辑自己的资源；共享只授予有限查看/运行/使用；模型与平台密钥由管理员控制；观察员不看正文；人员禁用影响其资源执行与个人 API Key；资源转移由管理员操作；不提供用户物理删除。

未来若出现“多人编辑同一 Agent”“开发者属于多个项目”“员工离职业务不能中断”等需求，分别增加协作者编辑授权、项目空间、企业服务账号。不要通过放开全部资源访问来临时满足这些需求。
