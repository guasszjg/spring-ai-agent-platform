# 平台升级计划：MCP、Skill 与知识库

后续会接 DeepSeek 这类支持工具调用的大模型。为了让智能体能接更多外部系统、处理更复杂的流程、答得更准，分三步升级：先做 MCP 客户端，让平台能直接接入现成的工具服务；再做 Skill 技能库，把处理流程做成能按需加载、跨智能体复用的模块；同时升级知识库检索，提高命中率，并让大模型能自己多次检索。

## 现状

| 环节 | 现在怎么做 | 限制 |
| --- | --- | --- |
| 工具来源 | 内置工具（时间、联网搜索）＋ 用户配置的 HTTP 工具 | 每个新能力要么写代码内置，要么逐个配 HTTP 接口；一个 HTTP 工具只能描述一次简单调用 |
| 工具调度 | 平台自研 `AgentToolRegistry` 生成工具定义并执行；`OpenAiCompatibleClient` 负责多轮调用，最多 5 轮 | 结构清晰，新工具来源只要接进这个注册表就能复用整条链路 |
| 智能体配置 | 智能体的 `toolsConfig` 记录启用了哪些工具 | 只能按工具名勾选 |
| 调用记录 / 计费 | `ToolUsageService` 按智能体、按天统计 | 可以直接沿用 |
| 知识库检索 | 父子切片、向量＋关键词混合检索（RRF 融合）、Rerank、问题改写、语义缓存、OCR、知识图谱、FAQ、评测台、Dify 双引擎 | 关键词这一路不是 BM25，也没有中文分词，问法和原文措辞不同时很难命中；每次对话只检索一次，模型不能自己补查 |
| 处理流程 | 写在智能体提示词或场景模板里 | 流程一多，提示词变长、互相干扰，每次对话都要付这部分 token |
| 模型能力 | 所有通道一视同仁，都会收到工具定义 | 板子上的 1.7B 不支持工具调用，上下文只有约 4096，收到工具定义只会出错或超长 |

## 前置：通道能力与上下文窗口

已完成约 2 天

MCP 和 Skill 都依赖模型能调用工具。先给模型通道加一个能力标记，让小模型通道自动绕开这部分功能，不影响现在板子上的知识库问答。

- 模型通道新增「支持工具调用」开关；OpenAI、DeepSeek 等预置通道默认开，Ollama 和自定义通道默认关，由管理员确认后打开。
- 智能体当前走的通道不支持工具调用时，平台不发送工具定义，也不注入技能列表；智能体编辑页给出提示。
- 通道测试时可以加一项「工具调用测试」，用一个内置工具实际调一次，判断这个模型是否可靠。
- **新增「上下文窗口」字段（tokens）。**板子上的小模型要求输入加输出不超过 4096。平台按这个值预留输出，再自动收缩知识库内容和历史对话，不再把超长请求发给模型。不填时沿用现在的行为；以后接 DeepSeek 等大模型只要填一个更大的数。
- 这一项上线后，板子上的长度代理就有条件撤掉。

## 第一步：MCP 客户端接入

主体完成 · 待补验证优先级 高约 2–3 周

**目标：**管理员填一个 MCP 服务地址，平台自动拉取这个服务提供的全部工具；审核启用后，智能体可以像使用内置工具一样勾选使用，调用记录和计费沿用现有机制。

### 运行流程

管理员在「工具」里添加 MCP 服务：地址、鉴权方式、超时

平台连接服务，拉取工具列表（名称、说明、参数格式）并保存

管理员逐个审核工具，启用需要的那些

智能体勾选启用的 MCP 工具，与内置工具、HTTP 工具并列

对话中模型决定调用，平台转发给 MCP 服务，结果交回模型，并记录用量

### 范围

| 做 | 暂不做 |
| --- | --- |
| 远程 MCP 服务，传输方式支持 Streamable HTTP（主流）和 SSE（兼容旧服务）   鉴权：Bearer Token、自定义请求头；密钥加密保存，复用现有加密方式   手动或定时刷新工具列表；工具有变化时提示管理员重新审核   MCP 工具接入现有调用记录、计费、调试窗口的工具调用展示 | 本地命令方式（stdio）的 MCP 服务：需要平台在服务器上执行命令，安全风险高   OAuth 授权登录类 MCP 服务：交互流程复杂，放到后续版本   MCP 的 Resources、Prompts 两类能力：先只用 Tools   把平台自身暴露成 MCP 服务（放到后续可选项） |

### 后端改动

- **依赖：**引入 Spring AI 2.0.1 自带的 MCP 客户端模块。本机 Maven 仓库还没有这个包，第一次需要联网下载。
- **数据表（Flyway V36，可重复执行）：**
  - `mcp_servers`：名称、地址、传输方式、加密后的鉴权信息、超时、启用状态、上次连接状态和时间、创建人。
  - `mcp_server_tools`：所属服务、工具原名、平台内唯一名、说明、参数格式、审核状态、启用状态、工具定义的指纹（用来发现上游变化）。
- **工具注册：**在 `AgentToolRegistry` 里加 MCP 这一类来源。工具名统一加前缀，比如 `mcp_github__create_issue`，避免和内置工具重名。MCP 工具与博查、时间等现有工具并存，互不影响，密钥也分开保存。
- **工具分类：**审核 MCP 工具时给它标一个类别（搜索、地图、数据库、文件等），内置工具沿用现有类别，用于判断同类重复。
- **连接管理：**按服务缓存连接，失败自动重连；单次调用设超时；服务不可用时返回明确的错误给模型，不卡住整个对话。
- **结果控制：**工具返回内容过长时截断，并告诉模型「结果已截断」，防止撑爆上下文。
- **接口：**MCP 服务的增删改查、测试连接、刷新工具列表、工具审核与启用。

### 前端改动

- 「工具」页新增「MCP 服务」分区：服务列表、连接状态、添加和编辑弹窗、测试连接按钮。
- 服务详情里列出它的全部工具，可逐个启用，能看到每个工具的说明和参数。
- 智能体编辑页的工具选择里，MCP 工具按服务分组显示。
- 重复工具提示：同一个智能体勾选了多个同类工具时（比如博查联网检索和某个 MCP 搜索工具），编辑页给出提示，建议只保留一个，避免模型选择不稳定、重复计费。
- 调试窗口里展示 MCP 工具的调用参数和返回结果，方便排查。

### 安全

- 只有管理员能添加 MCP 服务；开发者只能在智能体里选用已启用的工具。
- 服务地址走现有的 `OutboundUrlValidator` 出站校验；生产环境默认不允许内网地址，需要时由配置项放开。
- 工具默认不启用，审核后才可用；上游工具定义变了，自动停用并提示重新审核，防止被篡改的工具说明诱导模型。
- 带写操作的工具（创建、删除、发送等）在审核时标记出来，后续可以加「调用前需要确认」。
- 审核时如果 MCP 工具和已启用的内置工具功能重复（比如另一个联网搜索），审核界面提示，由管理员决定是否启用。

### 验证方案

市面上已经有大量现成的 MCP 服务，第一步做完就能用真实服务验证。按由简到繁分三层，每层通过再进下一层。

| 层次 | 用什么 | 验证什么 |
| --- | --- | --- |
| 1. 协议是否通 | MCP 官方测试服务 `everything`，本地运行，不需要账号 | 连接、拉取工具列表、调用、参数传递、服务报错和超时的处理 |
| 2. 真实服务 | 高德地图 MCP（注册开发者获取免费 Key，提供远程地址），或魔搭 ModelScope / 阿里云百炼 MCP 广场上托管的服务 | 鉴权、真实网络延迟、中文场景下模型能否选对工具 |
| 3. 内部系统 | 平台测试库 ＋ Postgres MCP 服务（用 `mcp-proxy` 或 `supergateway` 把本地命令方式包装成 HTTP 地址） | 内网地址放行配置、只读权限、数据查询类问答 |

**调试工具：**开发时先用官方的 MCP Inspector 直连服务，确认服务本身的工具和返回值正常，再接入平台。出问题时容易分清是平台的问题还是服务的问题。

**说明：**社区里很多 MCP 服务只提供本地命令方式（stdio）。第一步只支持远程地址，这类服务要先用上面的包装工具转成 HTTP 地址再接入。

### 验收演示

在平台添加高德地图 MCP 服务，拉取到工具列表，启用「路线规划」和「天气查询」

智能体走 DeepSeek 通道，勾选这两个工具

调试窗口提问「明天从公司去机场要多久，会下雨吗」

能看到模型先后调用两个工具，给出综合回答

工具用量统计里出现这两次调用

### 验收标准

- 上面三层验证全部通过，验收演示能完整跑通。
- 服务断开或超时时，对话能正常结束并给出说明，不会一直转圈。
- 上游工具定义变化后，相关工具自动停用并提示重新审核。
- 走 1.7B 小模型通道的智能体完全不受影响。
- 调用次数出现在工具用量统计里，按工具分开统计。
- 智能体同时勾选博查和 MCP 搜索工具时，编辑页出现重复提示；博查等现有工具的功能和用量统计不受影响。

## 第二步：Skill 技能库

已完成优先级 中约 2 周

**目标：**把「遇到某类问题该怎么处理」写成独立的技能，挂到智能体上。平时只占一行描述，模型判断需要时才加载完整步骤；同一个技能可以被多个智能体复用。

### 运行流程

在「技能库」里新建技能：名称、什么时候用、详细步骤、需要的工具

智能体关联若干技能，和关联知识库的方式一样

对话时，系统提示里只列出各技能的名称和一句描述

模型判断某个技能适用，调用内置工具 `load_skill` 读取完整步骤

模型按步骤执行，过程中调用内置工具、HTTP 工具或 MCP 工具

### 范围

| 做 | 暂不做 |
| --- | --- |
| 技能的新建、编辑、版本记录，详细步骤用 Markdown 编写   技能声明需要的工具；智能体没启用这些工具时给出提示   按需加载：平台内置 `load_skill` 工具   导入和导出 `SKILL.md` 格式，能直接用社区现成的技能   技能的使用次数统计 | 技能里附带脚本并在服务器上执行：需要沙箱环境，单独评估   技能市场、跨组织共享   模型自动生成技能 |

### 后端改动

- **数据表（Flyway V38，可重复执行）：**
  - `skills`：名称、触发描述、详细步骤（Markdown）、需要的工具、所有者、是否系统内置、版本、启用状态。
  - `agent_skills`：智能体与技能的关联。
- **组装提示：**`AiChatService` 组装系统提示时附上技能目录（名称＋描述），并为该智能体注册 `load_skill` 工具。
- **加载控制：**单次对话里同一技能只加载一次；技能正文设长度上限，超出时在编辑页提醒。
- **权限：**沿用知识库的规则，开发者管理自己的技能，管理员管理全部和系统内置技能。
- **接口：**技能增删改查、导入导出、关联到智能体。

### 前端改动

- 新增「技能库」页面：列表、编辑器（左边写 Markdown，右边预览）、导入导出按钮。
- 智能体编辑页增加「技能」选择，与「知识库」并列。
- 调试窗口里显示本次对话加载了哪些技能。

### 验收标准

- 一个智能体挂 10 个技能，日常对话的提示词长度只增加技能目录这部分。
- 问到某类问题时，调试窗口能看到模型加载了对应技能并按步骤执行。
- 从社区下载的 `SKILL.md` 能直接导入使用。

| 3.8 | 检索路由：智能跳过检索 · 后续 | 「先检索后回答」模式下，寒暄、问身份等问题不检索；检索结果明显不相关时不把资料塞进提示词。板子上寒暄类问题首字预计从约 2 秒降到约 0.5 秒 | 中 | 约 3–4 天 |

### 3.1 BM25 ＋ 中文分词

- **方案：**在平台程序里实现 BM25，中文用 jieba 分词，不依赖数据库扩展。板子和服务器都能直接用；ParadeDB、zhparser 这类数据库扩展需要单独安装，板子上更麻烦。
- **索引：**分词结果和词频随切片一起保存；切片新增、修改、删除时同步更新。切片写入的入口比较多，要统一走一个地方，避免漏同步。
- **词表：**支持按知识库添加自定义词，比如产品型号、内部术语，保证这些词不被切散。
- **融合：**替换现在的关键词一路，仍和向量检索一起用 RRF 融合，再走 Rerank。
- **风险：**知识库很大时词表和倒排数据会变大，需要测一下检索耗时；板子内存有限，要单独看。

### 3.2 切片上下文标题

- 解析文档时记录标题层级，生成切片时把「文档名 › 一级标题 › 二级标题」放在切片开头，再做向量化和分词。
- 回答时引用的原文仍显示切片正文，标题只用于检索。
- 已有知识库需要重建一次索引；提供「重建」按钮，后台逐个处理。

### 3.3 知识库作为工具

- 给智能体注册内置工具 `search_knowledge`（参数：查询词、可选的知识库范围、返回条数），复用第一步的工具调用、用量统计和调试展示。
- 智能体可以选择检索方式：「先检索后回答」（现有方式）或「模型自主检索」。
- 当前通道不支持工具调用时（比如板子上的 1.7B），自动退回「先检索后回答」，不影响现有效果。
- 单次对话的检索次数和返回总长度设上限，控制成本和上下文长度。

### 3.8 检索路由：智能跳过检索（后续实现）

现状：「先检索后回答」模式下每条消息都先检索知识库，「你好」也不例外。板子上实测「你好，你是谁？」仍要读约 2800 token 的资料，首字约 2.1 秒，其中约 1.6 秒是模型在读提示词；无关问题也会被塞进最接近的资料，小模型容易照着无关资料编答案。目前唯一的「路由」是 3.3 的模型自主检索，但它需要能稳定调用工具的模型，板子上的 1.7B 用不了。

| 做法 | 是否采用 |
| --- | --- |
| **寒暄规则**：问候、感谢、问身份等短消息直接不检索（用词表判断，可调整） | 采用：几乎没有成本，对板子帮助最大 |
| **相关性门槛**：照常检索，但最好的结果也明显不相关时，不把资料放进提示词，由模型按智能体自己的规则回答。用最高一条的向量相似度和 BM25 是否命中来判断，不用融合分（融合分没有绝对含义） | 采用：无关问题提示词更短、少被误导 |
| 先让模型判断要不要检索（多一次模型调用） | 不采用：板子上多一次调用比省下的检索还慢 |
| 按知识库描述选择检索哪些知识库 | 暂不需要：智能体通常只关联一两个知识库 |

- 智能体级开关，默认开启；需要每次都检索的智能体可以关掉。
- 门槛用数据定：87 道评测题必须全部照常拿到资料，另外准备一批寒暄、无关问题（应该被拦下）一起校准；被门槛误拦的问题逐条列出。
- 主要风险：门槛太高会把「运维诊断」这类短但需要知识库的问题拦掉，所以先校准再开发。
- 和模型网关的主备通道路由是两回事：那个决定用哪个模型，这里决定要不要检索。

### 3.9 文档图文配图（后续实现）

详细方案单独成文：[《文档图文知识库与回答配图实施计划》](https://github.com/guasszjg/spring-ai-agent-platform/blob/main/docs/%E6%96%87%E6%A1%A3%E5%9B%BE%E6%96%87%E7%9F%A5%E8%AF%86%E5%BA%93%E4%B8%8E%E5%9B%9E%E7%AD%94%E9%85%8D%E5%9B%BE%E5%AE%9E%E6%96%BD%E8%AE%A1%E5%88%92.md)（后端仓库 `docs/` 目录）。这里只列要点：

- 解析 Word、PDF 时在正文里图片所在位置插入图片标记，切片时按位置把图片关联到切片；回答命中这些切片时一并返回原图、图注和来源页码 / 章节。不做多模态检索，也不声称模型看懂了图片。
- 知识库新增「纯文字 / 图文关联」模式，默认纯文字（与现在完全一致）；智能体关联的多个知识库可以混合，图片只来自实际用到的图文知识库切片。
- M1：Word 优先，再做文字层 PDF；两张新表加一个知识库模式字段；复用「重建索引」补处理旧文档。外网图片链接不拉取，只显示为链接。Markdown / HTML / PPTX、OCR 与视觉描述、MinerU 等放到后续阶段。

### 验收标准

- 3.1、3.2 上线前后各跑一次评测台：整体命中率提高，原来能答对的用例没有变差。
- 专门准备一批「问法和原文措辞不同」「带型号或错误码」的评测用例，这类用例的命中率明显提升。
- 3.3：在调试窗口能看到模型多次调用 `search_knowledge`，回答引用了多篇文档；切到 1.7B 通道时自动用原有方式，回答正常。
- 检索耗时没有明显变慢，板子上单独测一次。
- 3.8：87 道评测题全部照常检索；寒暄、无关问题不再注入资料，板子上这类问题首字明显变快。

**排期关系：**3.1、3.2、3.4 不依赖 MCP，可以和第一步并行，由另一个人做；3.3 放在第一步之后，复用同一套工具调用和审核机制。

## 可选：知识图谱

后续可选 · 未开工满足启动条件再排期

**结论：**暂不作为正式步骤。先观察评测数据和真实提问，出现明确需求再做；在那之前保留现有试点，不接入智能体对话。

### 现状

- 平台已有 GraphRAG 试点：入库时用固定句式（「A 是／包含 B」「名称：值」）从切片里抽取实体关系三元组，抽取质量有限，不少是「格式支持 → jpg、gif…」这类碎片。
- 智能体对话不使用它，只在知识库「检索测试」页手动打开「GraphRAG 实体多跳图谱检索 (Pilot)」时生效；另有一个图谱可视化弹窗。

### 为什么现在不做

- **当前问题用不上：**产品手册、FAQ 以「查一个事实」为主。上 BM25 后，87 道评测题里 86 道能把正确资料交给模型（99%），图谱能提升的空间很小。
- **成本高：**能用的图谱要靠大模型逐个切片抽取实体和关系，板子上的 1.7B 做不了；用 DeepSeek 时入库变慢并产生费用。实体合并（如「广告机」和「终端」）、文档更新后同步图谱也需要持续维护。
- **还没有证据：**评测台已经可用，先用数据说话。

### 启动条件（满足任意一条）

- 真实对话里关系类、跨文档类问题较多：评测集里单独建一个分类，至少 20 道，Top3 命中率持续偏低。例如「功能 A 依赖哪些模块，这些模块由谁负责」，或需要汇总多篇文档的问题。
- 出现以结构化关系为主的知识库，比如组织架构、设备拓扑、零部件清单。
- 平台接入了成本可接受、可以批量抽取的大模型。

### 真做时的方向（粗略）

- 用大模型抽取实体和关系，替换现在的固定句式；做实体合并和别名表。
- 文档更新时增量更新图谱，复用 3.5 的增量机制。
- 作为检索的一路接入（或做成 `search_graph` 工具，复用 3.3 的工具化方式），先在评测台上和现有检索对比，效果更好才接入智能体。
- 工期另行评估；按经验抽取和维护部分约 2–3 周。
